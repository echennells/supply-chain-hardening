# Limitations

Every entry below is a boundary the role knows about and does not close. Most
are marked MEASURED — the behaviour was observed on a real host with the
version named, not inferred from documentation. `supply-chain-verify` reports
the ones it can detect as `WEAK` or `GAP`; the rest are structural and are
documented here so nobody mistakes the role for a sandbox.

For the reasoning behind what is and is not in scope, see
[design-principles.md](design-principles.md).

## Scope (and what is deliberately out of it)

This role hardens **language package managers** — the ecosystems in the
protection matrix. It does **not** harden the OS package layer (`pacman`, `apt`, and
especially the AUR) or the browser: those have their own trust mechanisms
(distro signature verification; for the AUR, reading the `PKGBUILD` before you
build), and no env var or package-manager config can stand in for them. Judging
this role against distro/AUR risk measures it against a threat it never claimed.

## Known boundaries

- **The Ansible role supports Linux only.** Its preflight refuses a macOS target before anything is written. MEASURED on GitHub's macos-15 before it did: the play replaced `~/.npmrc`, wrote `/etc/npmrc` and stopped at that file's group (`failed to look up group root`), with nothing after it applied, while `--preflight` said nothing would stop it. The env layer, the refresh timer and the group names are all Linux's. On a Mac use `action/harden.sh --emit=plain`, or the Action on a macOS runner; CI runs real attacks against that on macos-15 and macos-15-intel. A Mac as the controller of a Linux host is fine. The per-user paths differ there: pnpm's is `~/Library/Preferences/pnpm` unless `XDG_CONFIG_HOME` is set.
- **Not a sandbox.** Env vars and config files can be overridden by any process running as the same user. This protects against naive installs, not determined bypass.
- **A file in the working directory can shadow a Python stdlib module, and the role does not stop it by default.** MEASURED on cpython 3.13.12: a hostile `struct.py` beside a script executes on `import base64`, because stdlib `base64` does `import struct` internally — the caller never names the shadowed module. `python app.py`, `python -m base64` and `python -c "import base64"` all execute it; 273 of Python's 290 stdlib module names are shadowable (the 17 that are not are already imported at interpreter startup: `os`, `sys`, `io`, `codecs`…). **Already safe without any setting:** an installed console-script (`ruff`, `pytest`, anything pip-installed) is immune even in a hostile directory, because its `sys.path[0]` is its own bin directory rather than the cwd. The exposed case is specifically *writing a script into an untrusted directory and running it* — an agent unpacking an archive, or CI running a checked-out script. Set `python_safe_path: true` to export `PYTHONSAFEPATH=1`, which closes all three forms. **It is off by default because it breaks legitimate code at runtime:** `python script.py` importing a sibling module, and `python -m` against a local uninstalled package, both start raising `ModuleNotFoundError` — with an error naming neither this role nor the protection, which is the [attribution test](design-principles.md) failing. Installed tooling is unaffected. Requires Python 3.11+; below that the variable is inert and the role records the gap in `skipped_protections` rather than implying coverage. Turn it on where "a script imports a file sitting next to it" is closer to the threat than to the workflow — a dedicated agent host (`agent_host: true` turns it on there, with `uv_exclude_newer_env` and `verify_fail_on_gap`) — and not where people run their own code from checkouts. `python -I` (isolated mode) is the stronger per-invocation equivalent and predates 3.11; `python -E` does **not** help, as it only ignores `PYTHON*` env vars and never touches `sys.path`.
- **CLI flags beat config files in pip — but the age gate now reaches `python3 -m pip` anyway.** `python3 -m pip install --no-binary :all: --break-system-packages malicious-pkg` still bypasses both the `/usr/local/bin/pip` wrapper (because `python3 -m pip` invokes the module directly, not the binary) and the `/etc/pip.conf` `only-binary=:all:` setting (pip's CLI flags outrank config), so **sdist / `setup.py` admission remains defeatable by a caller who passes flags**. What is no longer true is that this caller is *ungated*: pip 26.0 added `--uploaded-prior-to`, and the role now deploys it as `uploaded-prior-to` under `[global]` in `/etc/pip.conf` and as `PIP_UPLOADED_PRIOR_TO` in the env layer, so the publish-age gate applies to the module caller too. MEASURED on a real Ubuntu 24.04 host after an apply, with the deployed cutoff `2026-10-19T00:00:00Z`: `python3 -m pip install pip==26.2.2` (uploaded 2026-10-20) is refused and the candidate list is truncated at `26.2.1`, while the same command with the key suppressed installs it. The key MUST be under `[global]` — under `[install]` it does not cover `pip download`, `pip wheel` or `pip index`. On pip below 26 it is accepted and silently ignored (measured rc=0 with zero bytes on stderr across ten pre-26 pips, 20.0.2 through 25.3), and `supply-chain-verify` reports such a host as `GAP`, never `OK`. A caller can still widen the window for one invocation by passing `--uploaded-prior-to` itself, exactly as `--exclude-newer` works for uv. Recommend `uv pip install` for callers that need pip's interface: it additionally applies `no-build`, which pip's config layer cannot defend against a flag.
  **Which interpreters actually carry a capable pip** (MEASURED 2026-10-21; every one of these reads the same
  `/etc/pip.conf`, so the key is pre-positioned and activates per-interpreter with no re-apply):

  | interpreter | pip | gate active? |
  |---|---|---|
  | Ubuntu 22.04 / 24.04 / 26.04, Debian 12 — apt `python3-pip` | 22.0.2 / 24.0 / 25.1.1 / 23.0.1 | no |
  | `python3 -m venv` on those hosts (`ensurepip` seeds the distro pip) | same as above | no |
  | `python:3.12-slim` image | 25.0.1 | no |
  | **`python3 -m pip` on a uv-managed CPython** | **26.0.1 – 26.2.1** | **yes** |
  | `python3 -m venv` from a uv-managed CPython 3.13.12 (`ensurepip` seeds its bundled pip) | 25.3 | no |
  | **`uv venv --seed`** | **26.3** | **yes** |
  | **`python:3.13` image** | **26.2.1** | **yes** |

  No apt-shipped pip carries it on any release the role declares, so upgrading the distro does not close the gap —
  which is why `supply-chain-verify` reports `GAP` on those hosts rather than `OK`. In practice the gate covers
  the pip of a uv-managed interpreter, recent official images, `uv venv --seed`, and any venv where pip has been
  upgraded; on a stock-distro interpreter the Python age gate remains the `uv pip` redirect, not pip itself. A venv
  does not inherit its interpreter's pip: `python3 -m venv` seeds whatever `ensurepip` bundles, so on CPython 3.13.12
  a gated base pip still produces an ungated venv (MEASURED: pip 25.3 took the newest `six` under a cutoff 26.3
  honoured). `supply-chain-verify` reports that as `pip venv age gate`. The `python:3.13` image was not checked for this.
- **uv's `no-build` blocks source builds** — `uv pip install .` from a local project, `uv pip install --no-binary :all: …`, and any install that must compile a wheel from an sdist (MEASURED, uv 0.12.7). A pure-Python *editable* install (`uv pip install -e .`) is a PEP 660 install and is not blocked; an editable install that has to compile is. **Your own project is blocked too on uv 0.12.5 and older:** `uv sync` and `uv run` in a project with its own `[build-system]` fail with ``error: Distribution `myproj==0.1.0 @ editable+.` can't be installed because it is marked as `--no-build` but has no binary distribution`` (exit 2). From uv 0.12.6 uv builds the project itself (MEASURED 2026-11-20 on uv 0.8.17, 0.9.16, 0.9.17, 0.11.16 and 0.12.5 against 0.12.6, 0.12.7 and 0.13.9; uv 0.12.6's changelog: "Allow explicit `uv build` and non-editable first-party workspace packages when `no-build` is enabled"). On the older uv, `supply-chain-allow-build uv sync` builds it; see [day-one.md](day-one.md). When you need to build something you trust, use the deployed helper `supply-chain-allow-build -- uv pip install .` rather than uv's built-in overrides: `--no-config` drops *all* config and `--config-file` / `UV_CONFIG_FILE` *replace* discovery, both silently dropping the other four hardened settings (index-strategy, exclude-newer, verify-hashes, allow-insecure-host). The helper mirrors the current hardened `uv.toml`, flips only `no-build`, scopes it to the one command, and logs what actually built. Honest residual: uv cannot scope build permission per package, so the build engine is open for that whole command — trust the source you point it at. See [design-principles.md](design-principles.md) ("Safe-by-construction overrides").
- **uv's `exclude-newer` and pip's `uploaded-prior-to` are absolute instants, so they only roll if something advances them.** The role sets both to *(apply time − `release_age_hours`)*, rounded down to midnight UTC — that is how the Python age gates work: uv and pip refuse any distribution *published* after that instant. The relative forms that would roll on their own are hard errors on older tools (pip 26.0 rejects `P2D`, uv ≤ 0.9.16 rejects `"48 hours"`), and `/etc/pip.conf` and `/etc/uv/uv.toml` are read by every interpreter on the host, so the role keeps the absolute form and, **on Linux hosts running systemd**, installs `supply-chain-age-gate-refresh.timer`, which re-runs the same formula every 6 hours and rewrites only the role's own cutoff lines (`/etc/uv/uv.toml`, `/etc/pip.conf`, `/etc/profile.d/supply-chain-hardening.sh`, and the deploying user's `uv.toml` and `pip.conf`). Residuals: a shell that is already open keeps the `PIP_UPLOADED_PRIOR_TO` it logged in with (the env var outranks `pip.conf`) until it is re-opened; a config file that is a symlink, or whose cutoff line is missing or duplicated, is left alone and logged; and other users' `~/.config` files are never touched. These files are role-managed, so a cutoff *value* edited by hand is advanced at the next run (logged as `old -> new`), just as a re-apply would overwrite it — to hold a cutoff during an incident, pin it (below) or `systemctl disable --now supply-chain-age-gate-refresh.timer`. **Without systemd** (most containers) the window does not advance: a legitimate release published since the last apply is refused until you re-apply the role or run `/usr/local/sbin/supply-chain-age-gate-refresh` (deployed on every Linux host) from cron: as root with no argument (which also covers root's own files when root deployed the role), plus `--user` as the deploying user otherwise. Either way `supply-chain-verify` reports a cutoff older than 7 days as a `WEAK` freeze rather than `OK`. To hold a cutoff still on purpose, set `uv_exclude_newer` / `pip_uploaded_prior_to` to an explicit instant instead of the default `rolling` — a pinned value is never advanced, even one equal to today's cutoff — or set `age_gate_refresh: false`. Do not lower `release_age_hours` to get fresher dependencies; that weakens the gate for everyone and every ecosystem. For a single trusted command, `uv pip install --exclude-newer <ISO-8601-date>` overrides only that one setting (unlike `--config-file` / `UV_CONFIG_FILE`, which *replace* config discovery and silently drop the other hardened keys); it widens the window for that invocation alone.
- **The uv cutoff is written into every project's `uv.lock`, so a moving cutoff moves the lockfile.** uv records the `exclude-newer` it resolved with in the lockfile's `[options]` table and treats a different value as a reason to resolve again. MEASURED with a one-dependency project on uv 0.11.7, 0.11.8, 0.12.9, 0.12.10 and 0.13.9:
  - **The refresh timer, on uv 0.12.9 and older.** After the cutoff advances by a day, `uv lock --check` and `uv sync --locked` fail ("The lockfile at `uv.lock` needs to be updated"), and a plain `uv run`, `uv sync` or `uv lock` rewrites the `exclude-newer` line, so every project's lockfile gains a one-line diff each day. uv 0.12.10 and later accept a lockfile whose cutoff only moved later and leave the file untouched.
  - **A lockfile shared with a host that has a different cutoff, on every version measured.** A lockfile made with no cutoff (an unhardened teammate) fails `--check` / `--locked` on the hardened host, and `uv lock` there writes this host's cutoff into it; a lockfile made on the hardened host fails the same way on an unhardened CI job. A cutoff moved earlier (a pin to an older instant) fails as well.
  - **The GitHub Action** computes its cutoff to the second on every run rather than rounding to midnight, so on uv 0.12.9 and older a job that runs `uv sync --locked` fails against a lockfile made under any other cutoff (a cutoff 60 seconds later was already enough). On 0.12.10 and later it passes only when the lockfile's cutoff is earlier than the job's; a lockfile made with no cutoff still fails, as above.
  - **Not changed, and why.** A relative span (`exclude-newer = "2 days"`) is recorded as a span (with a fixed placeholder timestamp from uv 0.11.8) and did not change the lockfile as days passed (MEASURED with the clock moved a day by libfaketime). The role does not write one because a span is a parse error on old uv (uv <= 0.9.16 rejects `"48 hours"`; see `uv_exclude_newer` in `defaults/main.yml`), which breaks every uv command that reads the file, and the files the role writes are read by every uv on the host. A span also does not help the shared-lockfile case.
  - **What to do.** Run uv 0.12.10 or later wherever lockfiles are committed. Harden the hosts that check a lockfile the same way as the hosts that write it. A project that has to pass `uv lock --check` on hosts with and without the role can pin its own `[tool.uv] exclude-newer` in `pyproject.toml`: it outranks the role's cutoff for that project, the lockfile then records the project's value, and `--check` passed on both kinds of host on every version above (MEASURED). That fixed value then *is* the project's age gate, so keep it at or before the role's cutoff. This holds while `uv_exclude_newer_env` is off, the default. Turned on, the exported `UV_EXCLUDE_NEWER` outranks the project's pin in a login shell, and the pin stops working (MEASURED 2026-11-21 with a `pyproject.toml` pinning 2024-05-01 under a host cutoff of 2024-10-01): on uv 0.8.17, 0.11.16 and 0.12.7 that project's existing lockfile fails `uv lock --check` and `uv sync --locked` on the host, and `uv lock` there rewrites its `exclude-newer` to the host's (0.8.17 and 0.11.16 also moved the packages forward); on uv 0.13.9 the existing lockfile still passes, but one written on the host records the host's cutoff and fails `--locked` wherever the variable is not set. For a project that sets no `exclude-newer` of its own, every `--locked`, `--frozen` and `uv lock` result was the same with the variable as with the `uv.toml` cutoff alone, on all four versions. The GitHub Action never exports the variable.
- **CLI flags beat env+config in npm too.** `npm install --ignore-scripts=false <pkg>` re-enables lifecycle scripts regardless of `/etc/npmrc`, `~/.npmrc`, or the `NPM_CONFIG_IGNORE_SCRIPTS` env var — npm's precedence puts CLI flags first. There is no clean interception (the wrapper at `/usr/local/bin/npm` passes args through; routing them through sfw doesn't help because sfw is a network-layer filter, not a lifecycle interceptor). Same broad-strokes situation as the pip bypass above. Don't expose hosts where untrusted callers can pass arbitrary npm flags and expect ignore-scripts to save you.
- **The bunx wrapper blocks fetching, not running what is already cached.** It injects `--no-install`, so `bunx <pkg>` never downloads anything — but a package bunx fetched *before* the role was applied, or through a deliberate unwrapped call (`<bun_real_path> x <pkg>`), stays in bunx's own cache and keeps running at that cached version (MEASURED, bun 1.4.4: `~/.bun/install/cache/.bunx-<uid>/`, or under `BUN_INSTALL_CACHE_DIR`; bun 1.4.3 kept it under `$TMPDIR`). That cached copy was never age-gated — bunx ignores the global bunfig. It is not a cross-user hole: bun ignores the cache unless the `.bunx-<uid>` directory is the current user's and not group/other-writable. To stop tools cached before the role from running, clear that directory after applying it.
- **npm ≥12 blocks dependency lifecycle scripts by default (native `allowScripts`).** On npm 12+, a dependency's `postinstall`/`preinstall`/`install` does not run unless explicitly approved (`npm install-scripts approve <pkg>`), independent of the role's config — MEASURED (npm 12.0.2): even `npm install --ignore-scripts=false` leaves it blocked (`npm warn install-scripts … not covered by allowScripts`). So the role's `ignore-scripts=true` is **redundant on npm ≥12** (npm blocks natively) yet stays **load-bearing on npm <12** and for any package a developer later approves via `allowScripts` (where `ignore-scripts=true` still refuses it). New friction to plan for: a *legitimate* dependency postinstall now needs `npm install-scripts approve` on npm 12+. The adversarial script-blocking tests are version-guarded to skip on npm ≥12 rather than pass tautologically (ECH-194).
- **Non-PAM contexts (Docker CMD, systemd units without `EnvironmentFile`, many agent processes) lose the env-var layer.** That makes the config files the only protection — and a user who controls their own home directory can write `ignore-scripts=false` to `~/.npmrc`, which beats `/etc/npmrc` per npm's `user > global` precedence. With the env var absent (because no PAM), the user override wins and the role's `/etc/npmrc` value is moot. In PAM-launched contexts (login, ssh, sudo -i, cron), the env var IS present and DOES beat `~/.npmrc` (env > user > global). Translation: trust the env-var layer for human workflows; trust the config-file layer for unattended workflows; if a user can modify their own dotfiles AND runs outside PAM, neither layer is fully protective. **Go has no config-file layer from the role at all:** `GOSUMDB`, `GOPROXY`, `GOTOOLCHAIN=local` and the `GOPRIVATE`/`GONOPROXY`/`GOINSECURE`/`GONOSUMDB` blanks reach Go only through `/etc/environment` and `/etc/profile.d`, so outside PAM Go runs with its own defaults. Several of those already match (`GOPROXY`, `GOSUMDB`). `GOFLAGS` is not written at all: Go's default build mode already refuses to change `go.mod`/`go.sum` (readonly since Go 1.16, or `vendor/` when the module vendors), and an explicit `-mod=readonly`, which earlier versions of the role wrote, made Go ignore `vendor/` (MEASURED on go1.22.12 and go1.27.4; see `goflags_mod` in `defaults/main.yml`); what is lost is `GOTOOLCHAIN=local` (Go's default `auto` downloads and runs whatever toolchain a `go.mod` asks for). The blanks never cleared a `GOINSECURE`/`GONOSUMDB`/`GOPRIVATE` a user set with `go env -w`, in any context: Go treats an empty variable as unset and falls back to its env file (measured on go1.24.2 for all three, and on go1.27.4 for `GONOSUMDB` and `GOPRIVATE`), so they only replace a value inherited through the environment; `supply-chain-verify` reports a checksum-database exemption from that file as a GAP and names it. The GitHub Action also persists them with `go env -w` (Go's per-user env file, which Go reads on every invocation); the role does not yet.
- **Repo-local configuration can outrank the role's user + system config.** Most package managers read a config file from the *current directory* at higher precedence than the `~` and `/etc` files the role deploys, so a hostile repository — or an agent unpacking an archive into a working directory — can weaken hardening without touching anything the role wrote. This is analysed in depth for cargo below; MEASURED for two more on Ubuntu 26.04:
  - **npm** — a repo-local `./.npmrc` with `ignore-scripts=false` re-enabled a dependency postinstall **in non-PAM contexts** (agent / CI / Docker `CMD`). In PAM contexts the `NPM_CONFIG_IGNORE_SCRIPTS` env var still wins (env outranks a project `.npmrc`), so this is the same shape as the "Non-PAM contexts" bullet above — bounded to where the env layer is absent. `allow-git=all` in a project `.npmrc` is the same: `NPM_CONFIG_ALLOW_GIT=none` outranks it where the env layer is loaded (MEASURED on npm 11.9.0 to 12.2.3), and both surfaces export that variable for npm 11.9.0 and newer, and for npm older than 11.2.0. The variable was added because the files alone were not enough even in CI: `actions/setup-node` with `registry-url` exports `NPM_CONFIG_USERCONFIG` at its own `.npmrc`, so npm skips `~/.npmrc`, and its npm reads its own prefix's `etc/npmrc`, never `/etc/npmrc`; with only the files, a git dependency installed there (MEASURED on npm 11.19.1). Below npm 11.9.0 there is no git block at all: npm ignores the key (11.8.0 installed a git dependency with it set). npm 11.2.0 to 11.8.x warn `Unknown env config "allow-git"` about it on every command, so neither the key nor the variable is written for them; `min-release-age` is left out for 11.2.0 to 11.9.x for the same reason. Below 11.2.0 both are written: nothing is printed, and a newer npm installed later honours them (see `sch_npm_writes_*` in `defaults/main.yml`; `action/harden.sh` has the same rule).
  - **uv** — a repo-local `./uv.toml` (or `pyproject.toml` `[tool.uv]`) with `no-build = false` re-enabled source builds in **every** context, PAM included, and its `exclude-newer` replaces the role's cutoff. uv's project config outranks the user and system `uv.toml` the role writes. Two uv variables outrank it in turn (MEASURED 2026-11-20 on uv 0.8.17, 0.9.16, 0.9.17, 0.11.16, 0.12.7 and 0.13.9):
    - `UV_EXCLUDE_NEWER` beats a project's `exclude-newer` for `uv pip compile` and `uv lock`, including `exclude-newer = false` (which uv 0.11.16 and older reject as a parse error). A project's `exclude-newer-package` still loosens it per package, and a command-line `--exclude-newer` beats it. **The role exports it only with `uv_exclude_newer_env: true`** (default `false`), set to the same cutoff as `uv.toml` and advanced by the refresh timer; it is in `/etc/profile.d` only, like `PIP_UPLOADED_PRIOR_TO`. It is off by default because it also beats a project that pins an *earlier* cutoff, which breaks the lockfile advice in the bullet above (measured there). Turn it on where uv runs in repositories nobody vetted, such as an agent host (`agent_host: true` does). With it on, the residuals are: login shells only (cron, systemd units and a container `CMD` get the project's value), a shell that was already open keeps the cutoff it logged in with, `exclude-newer-package` and `--exclude-newer` still win, and only an absolute RFC 3339 instant is exported (a pinned date or span is not, and the run summary says so: an empty value is exit 2 on every uv, a span is exit 2 on uv 0.9.16 and older). `supply-chain-verify`, run from inside such a repository with the variable set, reports the masked override as `WEAK` and names the variable; without it, `GAP`.
    - `UV_NO_BUILD=1` beats a project's `no-build = false` for `uv sync`, `uv lock` and `uv run`. **Not exported, by decision.** Every `uv pip` command ignores it (they declare no `UV_NO_BUILD` binding), so `uv pip install`, which the `pip` wrapper runs, still builds in that directory; with it exported `supply-chain-allow-build` is refused (uv's own `--build` is exit 2 next to it, so there is no per-command escape either); and an empty `UV_NO_BUILD=` is exit 2 on every project command. All MEASURED on the same six versions.

    `UV_CONFIG_FILE` would not help: it *replaces* config discovery — the same footgun `supply-chain-allow-build` exists to avoid — and breaks legitimate project settings. So on a default install a `uv.toml` committed to an untrusted repo is a complete bypass of the uv layer for anyone running uv inside that directory.
  - **pnpm 11+** — a repo-local `pnpm-workspace.yaml` outranks the role's global `config.yaml`, and the env layer outranks the workspace file (MEASURED on pnpm 11.0.0, 11.0.9, 11.28.13 and 12.21.0). The role exports `pnpm_config_minimum_release_age` (lower case; the upper-case form is read only from 11.0.6), so in a PAM session a workspace `minimumReleaseAge: 0` no longer lifts the gate, and `pnpm_config_minimum_release_age_exclude`, carrying the operator's own `pnpm_minimum_release_age_exclude` as a JSON array, `[]` by default (pnpm 12 ignores an empty value), so on a host a workspace `minimumReleaseAgeExclude` list cannot exempt the package an attack ships. The action exports neither: in CI the repository is the project being built, the age variable would cut a project's longer window down to the action's, and the exclude variable would wipe a project's own list; its `config.yaml` still applies to a project that sets neither. Three things stay open:
    - **`ignoreScripts: false`** in a repo's workspace file still runs the repo's own `postinstall`, and the builds its `allowBuilds` names; pnpm's approve-builds gate still refuses the rest. `pnpm_config_ignore_scripts` is not exported, by decision: `true` also silently skips a build a project approved with its own `ignoreScripts: false` + `allowBuilds`, the per-project route described below (exit 0, no message: MEASURED on 11.0.9, 11.28.13 and 12.21.0), and `false` would override a project's own `ignoreScripts: true` (measured on the same versions).
    - **Non-PAM contexts** (systemd units, a container `CMD`) do not get the variables, as for npm. Debian and Ubuntu cron get them from `/etc/environment`.
    - **pnpm 10** reads neither variable, and `npm_config_*` loses to its workspace file. A project `.npmrc` `minimum-release-age` outranks the host too on pnpm 10 (MEASURED, 10.34.9); pnpm 11 no longer reads it.

    `supply-chain-verify` and `action/verify.sh`, run from inside the project, report this in a `pnpm repo config override` row: `GAP` when the workspace switches the gate off (`0`, a negative number, and on pnpm 10 and 11 also `null`, `''`, `true` or `false`) or exempts `'*'`, `WEAK` for a shorter window, named exclusions or `minimumReleaseAgeStrict: false` (which lets a too-new exact pin install on pnpm 11.0.0, 11.28.13 and 12.21.0), and `WEAK` naming the variable when a `pnpm_config_*` variable in its own environment is what hides the project's value. It reads the file rather than asking pnpm: in a project, pnpm 10 and 11 run its pnpmfile and fetch its `configDependencies` for any command, `pnpm config get` included (MEASURED on 10.34.9, 11.0.0 and 11.28.13), so the verifier asks pnpm only from `/`.

    On a host hardened by the role, the env variables override a project's own values in both directions, so a project that chose a *longer* window, or listed its own fresh packages in `minimumReleaseAgeExclude`, gets the host's instead. pnpm records neither setting in `pnpm-lock.yaml`, so a lockfile does not change; but on 11.28.13 and 12.21.0 an existing lockfile that holds a version younger than the window now fails `pnpm install` and `pnpm install --frozen-lockfile` with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`, where that project's own `minimumReleaseAge: 0` used to let it through (11.0.9 and 10.34.9 do not check versions already in the lockfile). A lockfile made with no gate at all already failed the same way under the global `config.yaml` alone (all MEASURED 2026-11-21).
  - **Yarn** — a repo-local `.yarnrc.yml` with `enableScripts: true` and `npmMinimalAgeGate: 0` outranked the role's `~/.yarnrc.yml` (MEASURED with `yarn config get` on Yarn 4.10.3, 4.11.0 and 4.18.1, and a project `0` installed a 19-hour-old release on 4.19.0). `YARN_ENABLE_SCRIPTS` and `YARN_NPM_MINIMAL_AGE_GATE` in the environment outrank the repo file, but the role exports neither, and the second makes every command of Yarn 4.9 and older fail (``Usage Error: Unrecognized or legacy configuration settings found: npmMinimalAgeGate ... (in <environment>)``, MEASURED on 4.9.4). A repo can also bring its own yarn: a `yarnPath` (or classic's `yarn-path`) is the yarn that runs there, and `plugins:` load into it, for every command. `supply-chain-verify` and `action/verify.sh`, run from inside the project, report all of this in a `yarn repo config override` row, read from the files: `GAP` for a gate of `0`, `enableScripts: true`, an `npmPreapprovedPackages` entry that matches every package (`**`), every unscoped one (`*`) or every scoped one (`@*/*`), and a `yarnPath` whose version string is below 4.10; `WEAK` for a shorter window, named exemptions, plugins, and any `yarnPath`.

  The same class applies to the other ecosystems that read repo-local config. Bun: a project's `bunfig.toml` outranks the global one (MEASURED on Bun 1.4.5: `minimumReleaseAge = 0` and `minimumReleaseAgeExcludes` each installed a release the global gate refused, and `ignoreScripts = false` ran the install script of a package in `trustedDependencies`). pnpm 10's repo `.npmrc` was measured above. `action/harden.sh --suggest` lists these files for a repo, and reports a spelling it does not follow as not read. It is **not closable from a host-hardening role** — a repo config file is an open delivery surface and the tools read it by design. The mitigation is procedural, exactly as for cargo: do not run package managers inside a repository you do not trust, or do it in a container. See [design-principles.md](design-principles.md).
- **sudo clears the environment**, but config-file hardening still applies for the ecosystems with a system path (npm, pip, uv) via `/etc/*` deployment. pnpm never reads `/etc/npmrc`: pnpm 9 and 10 get script blocking only where npm's global config is `<node prefix>/etc/npmrc`, with no age gate, and nothing with apt's npm (see the pnpm allowlist entry below). Composer additionally writes to `/root/.config/composer/config.json` to cover the common case where `sudo composer …` lands with `HOME=/root`. Yarn has no system path: Yarn Berry reads `.yarnrc.yml` from the project, its parent directories and `$HOME` only, and never `/etc/yarnrc.yml`, which this role and the action used to write "for sudo and other users" (MEASURED on Yarn 4.9.4, 4.10.3, 4.11.0 and 4.18.1, as root and as a second user: its settings did not take effect, and on 4.9.4 to 4.11.0 a dependency postinstall ran with only that file in place). Both now write root's own `~/.yarnrc.yml`, which a `sudo yarn` reads (sudo sets `HOME=/root`: MEASURED with sudo 1.9.13p3 on Debian 12 and 1.9.15p5 on Ubuntu 24.04), and both remove an `/etc/yarnrc.yml` that carries one of this project's markers. Root's own file may hold a registry and its token, so when they run as a non-root user the role leaves one it did not write alone and lists it in the end-of-run summary, and the action copies it next to itself and warns before replacing it. Run as root with `HOME=/root`, root's file is the deploying user's own `~/.yarnrc.yml`, and is treated as any user's: the role stops on one that is not exactly what it last wrote, and the action copies it first. The same rule holds for root's copy as a non-root user: a token added to a `/root/.yarnrc.yml` this project wrote makes it root's own. macOS was not measured: if its sudoers keeps `HOME`, a `sudo yarn` there reads the invoking user's file. Every other account gets only Yarn's own defaults: on Yarn 4.10 to 4.13 that is install scripts on and no age gate; from 4.14.0 scripts are off by default, and from 4.15.0 there is a 1-day gate (MEASURED with no config file anywhere). Bundler has no system or /root coverage — `sudo bundle …` bypasses the per-user config and falls back to upstream defaults. Cargo: where cargo sits at a system path (apt's `/usr/bin/cargo`, `/usr/local/bin/cargo`), `sudo cargo build` and other accounts' builds stay gated: that wrapper names a root-owned copy of cargo-cooldown in `/usr/local/libexec/supply-chain-hardening/cargo/` and pins the window in the environment; `/root/.cargo/cooldown.toml` adds root's `[[allow.exact]]` rules. The wrapper no longer puts the deploying user's `~/.cargo/bin` on anyone's `PATH`. Before this, it put that directory first on `PATH` for every caller, and MEASURED (VM#2, reproduced on Ubuntu 26.04 with apt cargo 1.93.1): root and a second account ran the deployer's `cargo-cooldown` and `~/.cargo/bin/cargo`, and a second account's apply removed the first account's gate. Re-applying converges a host left in that state: the role also re-renders any older wrapper of its own at `/usr/local/bin/cargo` or `/usr/bin/cargo` that it no longer discovers first (for example after the deployer installs rustup), and `supply-chain-verify` reports a wrapper that still prepends another account's directory as `GAP`. A wrapper in one user's own `~/.cargo/bin` is not on the PATH that sudo's `secure_path` gives root; called by root or another account anyway, it refuses its backend with a `[supply-chain-hardening] error: refusing to run the cargo publish-age gate backend` message rather than run a file that user can replace. `~/.cargo/config.toml` remains per-user. Note that cargo reads config from `$CARGO_HOME`, which is **not** always `~/.cargo` (the official rust images set it to `/usr/local/cargo`); the role resolves it rather than assuming. Bun's install-time hardening (lifecycle scripts, age gate, frozen lockfile, scanner) is per-user only for the same reason; its runtime auto-install blocking is covered by the PATH wrapper at `/usr/local/bin/bun` regardless of caller UID.
- **An agent runner may never load the env layer, or may keep the one its session started with.** MEASURED on two agent VMs on 2026-11-26: one runs its commands with `bash --norc --noprofile` and no `BASH_ENV`, so it sources nothing from `/etc/profile.d/`, while the config files under its `$HOME` were still read; the other replays a shell state saved when the session began, so after a re-apply an older session keeps the earlier variables and aliases until a new one starts. What survives: on the first VM, marker files in `/root`, `/usr/local/bin` and `/etc` were gone after a redeploy and the one in its HOME was kept; on another, all of them survived a restart, and no redeploy of it has been observed (MEASURED, 2026-11-26/27). See [design-principles.md](design-principles.md#agent-runners).
- **Gradle and Maven read the passwd home, not `$HOME`.** Their default homes come from the JVM's `user.home`, which is the passwd home of the uid (MEASURED with maven 3.10.2 and gradle 8.14.8 on java 21.0.13.1: as root with `HOME=/tmp/h`, both read `/root`). The role writes gradle's init script (when `GRADLE_USER_HOME` is unset) and Maven's `settings.xml` there, looked up by uid, and its run summary names both homes when they differ. A host that keeps only `$HOME` across a rebuild loses both files with the rest of the passwd home. Where the account has no passwd home it can write, the role writes them under `$HOME`, and lists them as not applied unless `$HOME` is that passwd home. `action/harden.sh` writes both to the passwd home too, looked up by uid, says so when that is not `$HOME`, and points `GRADLE_USER_HOME` at gradle's; with `--home-only` it writes neither outside `$HOME`.
- **Eleven per-user files are replaced, not merged, so a registry or token you keep in one has to be put back by hand.** `~/.npmrc` is merged; pnpm's `config.yaml` and `rc`, `~/.yarnrc.yml`, `pip.conf`, `uv.toml`, the bunfig, `~/.bundle/config`, cargo's `config.toml`, Maven's `settings.xml`, `NuGet.Config` and Composer's `config.json` are not. A host whose private registry lives in one of them stops the role on every apply until the edit is moved or `accept_user_config_overwrite=true` is passed, and that leaves the registry in the copy, not in use. Keep it in the project's own file or in the tool's environment variables instead.
- **Lines kept in `~/.npmrc` can weaken what the block sets.** They are the user's, and keeping them is the point. `before=<date>` replaces `min-release-age` in either order (MEASURED on npm 11.19.1 and 12.2.3: with `min-release-age=36500` and a recent `before` the install went through), and `min-release-age-exclude[]` exempts packages. The run names `before`; it does not remove it. A longer `min-release-age` of the user's own stays and wins over the block, but `NPM_CONFIG_MIN_RELEASE_AGE` in the env layer, which holds this project's window, outranks the file wherever that layer is loaded: to lengthen the window everywhere, raise `release_age_hours`.
- **A `~/.npmrc` copy holds the tokens that were in the file.** One is made when a line had to be taken out, as `~/.npmrc.<pid>.<date>~`, 0600, and the run names it. Nothing deletes it. The same goes for the copies of the others. A run killed with `SIGKILL` in the middle of a write leaves the file as it was and can leave a `.sch-XXXXXX` (0600) next to it.
- **Composer's `config.json` is judged by its lines, not a checksum.** A change to it that only uses values this project could have written (a longer `period`, an `audit` switch) is overwritten without a word. So is a hand-edited cutoff in `uv.toml` or `pip.conf` in the exact shape the refresh timer writes.
- **Root writes only to paths no other account controls.** npm's global config in a prefix other accounts can write to (a group-writable `/usr/local`, another account's Homebrew) is left alone and listed in the run summary; so is root's own `~/.yarnrc.yml` or Composer `config.json` where a link in its path leads out of root's own directories. `sudo -E harden.sh`, and the role under a `sudo` that keeps `HOME`, write no per-user file in that home and say whose account to run as; the role does not write gradle's or Maven's file to root's own home instead. Root with another account's `HOME` and no sudo (a container job with `HOME=/github/home`) still writes there, as before, except for the role's gradle and Maven files, which go to root's passwd home (above).
- **Without pipelining, Ansible has root run files that belong to the connecting account.** For every `become` task, of any role, it puts a module file in that account's `~/.ansible/tmp` and root runs it from there (MEASURED on ansible-core 2.18.20 and 2.22.0: the account's own, 0764). That is Ansible's default and the role cannot change it: whatever runs as that account during an apply has to be trusted. With `ANSIBLE_PIPELINING=true` root runs none from there. The role's own script reaches root on stdin, so with pipelining it adds no file; `template` and `copy` tasks still put there what they install.
- **The cargo wrapper names a root-owned gate backend, but cargo may run another copy.** cargo, not the wrapper, starts cargo-cooldown (`cargo cooldown build`). cargo looks in the caller's `$CARGO_HOME/bin` first, unless that directory is on `PATH`, where `PATH` order decides; then it looks along `PATH`. The wrapper appends the root-owned copy's directory to the end. So that copy runs only when `$CARGO_HOME/bin` and the `PATH` entries hold no other `cargo-cooldown`; otherwise cargo starts the other file, and nothing checks it. Two cases are MEASURED. In the official rust images (`rust:1.100.0-slim-trixie`: `CARGO_HOME=/usr/local/cargo`, on `PATH`, directory mode 0777), the wrapper named the libexec copy, whether the role or `harden.sh` wrote it, but root's build ran `/usr/local/cargo/bin/cargo-cooldown`. After a second account replaced that file, root ran the replacement and nothing refused it. Any account can replace the wrapper, `cargo-real` and the rustup proxies in that directory just as easily, so in those images the toolchain belongs to every account. The second case is root running with another account's directory on its own `PATH` (`sudo env PATH=…`): root then runs that account's `cargo-cooldown`, as it would any other command found there. Making the wrapper check or redirect cargo's own lookup would refuse root in the stock rust images. That is an open decision.
- **On Debian hosts with `/etc/staff-group-for-usr-local`, the wrappers refuse their root-owned backends.** When that file exists, Debian's base-files makes `/usr/local`, `/usr/local/bin`, `/usr/local/libexec` and the other `/usr/local` directories `2775 root:staff` (base-files 13.8 postinst, read from source; a fresh trixie install has no such file, and the file's own template says it was created on upgrades from squeeze-era base-files). A member of `staff` can then replace anything in them, so both wrappers refuse those paths for every account, the deployer included. MEASURED (Ubuntu 26.04 container, modes set by hand): with `/usr/local` at `2775 root:staff`, the cargo wrapper refused the libexec copy with exit 126, naming `directory /usr/local`; with `/usr/local/bin` at `2775 root:staff`, root's `pip` refused a root-owned `/usr/local/bin/uv` with exit 126. Nothing at apply time tests this, so it shows only at the first build or install.
- **`bin`-link shadowing is neutralised by `ignoreScripts`, not by a trust list.** A package needs no lifecycle script of its own to run code: it can declare a `bin` entry whose name (`node`, `sh`, a build tool like `grunt`) shadows a command, which the package manager symlinks into `node_modules/.bin` before any script runs. If a *trusted* dependency's own postinstall then invokes that name, the shadow runs — the npm/bun PATH order puts `.bin` first. This was reported against bun's `trustedDependencies` in Nov 2026 ([BunnyHijack PoC](https://github.com/X3r0Day/BunnyHijack-PoC); the maintainer disputed it as a vuln) and, as that thread notes, the same PATH ordering exists in npm. The role's defence is mechanism-independent: `ignoreScripts = true` (bunfig) and `NPM_CONFIG_IGNORE_SCRIPTS=true` stop **every** lifecycle script — including a trusted dependency's, per [bun's docs](https://bun.com/docs/runtime/bunfig) verbatim ("both for your project and for packages in `trustedDependencies`") — so the shadowed bin is never invoked, and the 48h age gate refuses the carrier package regardless. Verified only as the general case: `15-bun-adversarial.bats` and `03-npm.bats` prove a postinstall is blocked; the specific trusted-dep→shadowed-bin chain is reasoned from those plus the PATH order, not reproduced. **Residual:** on bun < 1.2.0 the `ignoreScripts` key is inert (recorded in `skipped_protections`), so there the chain is open; a PATH wrapper cannot help because this is `.bin` resolution inside the installer, not a wrapped top-level call.
- **Bun's runtime auto-install gap is closed by a wrapper, not the config file.** `bun run script.ts` (the runtime entry point) silently downloads missing imports from npm — typosquat risk in CI/agent contexts. The `[install].auto = "disable"` knob in `~/.bunfig.toml` does NOT block this code path: per [bun's docs](https://bun.sh/docs/runtime/bunfig) verbatim, "Currently, bunfig.toml is only automatically loaded for `bun run` in a local project (it doesn't check for a global .bunfig.toml)." The role instead deploys `/usr/local/bin/bun` as a wrapper that injects `--no-install` on every non-package-management invocation. Real bun preserved at `/usr/local/bin/bun-real`. Package-mgmt subcommands (install/add/remove/update/upgrade/link/unlink/pm/outdated/why/audit/publish/patch/init/create) skip injection so they consult bunfig as normal. Bypass per-invocation: `bun -i script.ts` (explicit opt-in to fallback auto-install) or `/usr/local/bin/bun-real script.ts` (around the wrapper). Disable globally with `bun_path_wrapper=false`. Self-update caveat: `bun upgrade` writes a fresh binary to `~/.bun/bin/bun`; re-apply the role after upgrading to refresh wrapping.
- **`pip` is `uv pip`, so pip's own surface that uv lacks is refused, by name.** Where uv is installed, `/usr/local/bin/pip` and `pip3` run `uv pip` (see [how-it-works.md](how-it-works.md)). MEASURED on uv 0.9.9, uv exits 2 on `pip --version`, `pip download` and `pip install --user`, with its own text. The wrapper now answers `--version` itself (`uv-pip <uv version> from <path>`, exit 0). The second field is uv's version, not pip's, so a script that parses `pip --version` for pip's version reads uv's version (for example 0.9.9) and may take it for an ancient pip. It refuses `--user` and `download` before uv runs, with a `[supply-chain-hardening] error:` line naming the pip-to-uv wrapper and the route (`uv tool install` or a virtualenv for `--user`; `python3 -m pip download`, which runs pip under `/etc/pip.conf` without the uv settings). Installs need a virtualenv (`uv venv`) or `--system`, as uv requires. When uv refuses anything, the wrapper adds one `[supply-chain-hardening] note:` line after uv's error, naming those requirements and `supply-chain-allow-build` for a source build a person vouches for, and keeps uv's exit code. Which uv runs is chosen per caller: a uv the caller owns, or a root-owned one that no other account can replace (a root-owned uv in the caller's own directory counts as the caller's). So `sudo pip` on a host whose only uv is in a user's `~/.local/bin` is refused with a message, where it used to run that user's uv as root (MEASURED, VM#2); install a root-owned uv at `/usr/local/bin/uv` if root needs pip. Another account uses its own `~/.local/bin/uv` or `PATH` uv.
- **An activated virtualenv shadows the pip PATH wrapper, so the uv age gate does not apply inside it.** This is the venv form of the shim problem below, and it is far more common. MEASURED on a hardened Ubuntu 24.04 host: inside `python3 -m venv` + `activate`, `command -v pip` is the venv's own `bin/pip`, so `/usr/local/bin/pip` — and with it the `uv pip` redirect that carries `exclude-newer` — is never invoked. The split is clean and worth knowing: the **config layer survives** (the venv's pip still reads `/etc/pip.conf`, and `only-binary = :all:` was verified to refuse a locally-built sdist there while a control run with the config suppressed installed it), but the **age gate does not**, because `ensurepip` seeds the venv with the *distro's* pip — 24.0 on Ubuntu 24.04 — which ignores `uploaded-prior-to`. So in a stock-distro venv you get sdist blocking only for what pip resolves from an index or `--find-links`, and no publish-age gate at all. `only-binary` does not cover an sdist named by path or URL: `pip install ./x.tar.gz` runs its `setup.py` (MEASURED on pip 22.0.2, 23.0.1, 24.0, 25.1.1 and 26.0.1, in a venv and with system pip), and `supply-chain-verify` grades the row WEAK for that reason. `uv venv` does not have this problem: a plain one has no pip at all, `uv venv --seed` installs a current pip that honours the deployed `uploaded-prior-to`, and `uv pip install` is gated by `exclude-newer` regardless. Prefer `uv venv` / `uv pip` on hosts where the age gate is load-bearing, or upgrade pip inside the venv you care about.
- **On a host whose only Node is per-user (fnm, nvm, volta, asdf, nodenv), `sfw`, `npq` and `lockfile-lint` are not installed.** All three install system-wide as root, and root cannot run a per-user npm because sudo's PATH does not contain it (MEASURED on fnm, nvm, volta, asdf and nodenv: root finds no npm, and before this check all three installs ran, failed and were recorded as "install failed"). The role checks for that before installing and records the reason, naming the npm it found, instead of attempting an install that cannot work. It does not run the user's npm as root, which would let root execute files the user can edit: where sudo keeps the user's PATH (no `secure_path`), root does find that npm, so the check also requires root to own the npm and node it would run. Without sfw or npq the npm wrapper is not deployed either. This is reported, not silent: each is recorded as skipped, and the verifier prints a `GAP` for sfw and npq. Config-layer protections still apply. A system-wide Node lets both install, but while the version manager stays first on `PATH` the wrapper is shadowed (next entry).
- **On mise / asdf / volta / fnm hosts the PATH wrapper is shadowed by the shim.** A per-user version manager puts its shims directory (e.g. `~/.local/share/mise/shims`) ahead of `/usr/local/bin` on `PATH`, so a command like `npm` resolves to the shim, not the role's wrapper — MEASURED on an Omarchy/Arch host with a mise-shimmed npm. This splits coverage cleanly: the **config-layer** protections still apply (the shim runs a real tool that reads `~/.npmrc` / `/etc/npmrc` — `ignore-scripts` and the age gate work; verified behaviorally that a malicious postinstall was blocked), but the **wrapper-layer** protections that *only* the PATH wrapper provides are bypassed — for npm that is Socket Firewall routing and npq reputation checks; for cargo/deno/bun it is the flag injection (`--locked`, `--minimum-dependency-age`, `--no-install`). It is per-tool: only the tools the version manager shims are affected (a tool at a plain path like `/usr/bin/deno` is still wrapped). A system role cannot reliably win the PATH race against a per-user shim manager. `supply-chain-verify` reports the shadowed wrapper honestly (`GAP … npm resolves to a mise shim`). Where wrapper-layer coverage matters on such a host, wrap at the version-manager layer, or order `/usr/local/bin` ahead of the shims directory for the accounts that need it.
- **pnpm 11 has no system-wide config path.** pnpm 11 only reads `~/.config/pnpm/config.yaml` per-user. `sudo pnpm install` runs as root, which has its own (empty) config — meaning sudo'd pnpm 11 invocations are unprotected by this role. Workaround for hosts where this matters: also write the file to `/root/.config/pnpm/config.yaml`.
- **On pnpm 11+, build approval is per project, and `allowBuilds` alone is not enough under the default.** pnpm 11 explicitly rejects `onlyBuiltDependencies` in the global config file ("Move it to a project-level `pnpm-workspace.yaml`"), so the package names in `pnpm_built_dependencies` reach pnpm 10 only. MEASURED on pnpm 11.28.12 and 12.21.0 with a project depending on esbuild 0.25.0: under the role's default global `ignoreScripts: true`, a project's `allowBuilds: {esbuild: true}` installs with rc=0 and no message and esbuild's postinstall does not run; with no `allowBuilds` the build is skipped just as silently. The project needs `ignoreScripts: false` **and** `allowBuilds` in its own `pnpm-workspace.yaml` (a project file outranks the global one); every dependency it does not name is then refused loudly with `ERR_PNPM_IGNORED_BUILDS`, but the project's own lifecycle scripts (`postinstall` and friends in its `package.json`) run too. Setting a non-empty `pnpm_built_dependencies` makes the role write `ignoreScripts: false` to the global `config.yaml`, as the GitHub Action does, so every project's `allowBuilds` takes effect without the per-project line, at the cost of letting every project's own lifecycle scripts run. A repo can set `ignoreScripts: false` itself, so the global `true` does not hold a hostile repo's own scripts back either (MEASURED, same versions); see the repo-local config limitation.
- **pnpm allowlist is per-user, not system-wide.** Even on pnpm 10, the role's allowlist (`pnpm_built_dependencies`) only lands in the deploying user's `~/.config/pnpm/rc`. `sudo pnpm install` or another account sees only npm's global npmrc. Where that is `<node prefix>/etc/npmrc` (NodeSource, nvm, the node images), pnpm 9 and 10 read it and scripts stay blocked: this fails closed. **With apt's npm it fails open:** npm's global file is `/etc/npmrc`, pnpm reads `/usr/etc/npmrc`, and a project's own `postinstall` ran with no age gate (MEASURED, pnpm 10.34.9 on Debian 13). In both, the age gate reaches only the deploying user and login shells.
- **On a terminal, pnpm 11+ offers to exempt a too-new pin, and "y" writes the exemption into the project.** With no global `minimumReleaseAge` (pnpm's own default), `pnpm add <pkg>@<version published hours ago>` installs it and silently adds `<name>@<version>` entries to the project's `minimumReleaseAgeExclude` in `pnpm-workspace.yaml`. Under the role's `config.yaml` that silent write does not happen (MEASURED on 11.28.12 and 12.21.0 with a TypeScript nightly published ~10 hours earlier): with no terminal (CI, an agent without a pty) the install fails with `ERR_PNPM_NO_MATURE_MATCHING_VERSION` and nothing is written. On a terminal, pnpm instead asks "Add to minimumReleaseAgeExclude in pnpm-workspace.yaml and proceed with the install? (y/N)". Enter takes the default, No (`ERR_PNPM_MINIMUM_RELEASE_AGE_DENIED`, nothing written), but `y` installs the version and writes the same entries to the project file, where they exempt that exact version for everyone who uses the repository: a second user with the role's `config.yaml` and no terminal then installed it from that repository with rc=0, and without the file was refused with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` (MEASURED, same versions). The prompt is pnpm's and does not name this role. Anything that answers prompts in a pty can approve it, an agent included, so review `minimumReleaseAgeExclude` changes in `pnpm-workspace.yaml` like any other dependency change.
- **Yarn 1.x (classic) receives no yarn hardening at all.** Every yarn setting this role deploys lives in `~/.yarnrc.yml` (and root's), which is the Yarn 2+ "berry" format. Yarn classic does not read that file — it uses the unrelated ini-style `~/.yarnrc` — so on a host whose active yarn is 1.x, `npmMinimalAgeGate`, `enableScripts: false`, `checksumBehavior`, `enableImmutableInstalls`, and `enableHardenedMode` are all inert. There is no warning; `yarn install` simply behaves as an unhardened yarn. This bites by default on distros that ship yarn 1.22 from apt. Either activate a berry version (`corepack enable && yarn set version stable`, or pin `packageManager` in each project's `package.json`) or treat yarn as unprotected on that host and rely on the npm/pnpm layers. The adversarial test suite pins itself to a berry version so it measures the role's config rather than an unhardened classic yarn — so a green test run is not evidence that a yarn-1.x host is protected.
- **The role blocks exotic subdependencies on pnpm 11 only.** This control blocks a *transitive* dependency from resolving to a git / http(s) / tarball-URL source — per pnpm's docs, "only direct dependencies ... may use exotic sources." It governs SUBdeps, not the direct deps you list yourself, and it defaults to `true` in pnpm 11. The role writes `blockExoticSubdeps: true` to `~/.config/pnpm/config.yaml` so the setting is explicit and survives a config-precedence surprise. pnpm 10.26.0 to 10.34.9 have the control too, off by default, and honour `block-exotic-subdeps=true` in their `rc` (MEASURED with a tarball-URL dependency of a dependency; 10.25.0 has no such control). The role does not write it there, so on a pnpm 10 host a transitive exotic dependency is unblocked at the pnpm layer, the run summary lists it as not applied and `supply-chain-verify` reports a GAP; lockfile review plus the age gate are the remaining controls. The GitHub Action writes the key to `rc` as well. Checked against code.claude.com's permissions, settings-reference, headless, cli-reference and Agent SDK (TypeScript and Python) pages on 2026-11-20; the SDKs load project settings unless `settingSources` / `setting_sources` leaves them out.

  Because execution cannot be blocked, the role attacks the step before it: **refusing to resolve the malicious version at all.** The cargo PATH wrapper routes `build`/`check`/`test`/`run`/`update` through `cargo cooldown` (publish-age gate, default 48h from `release_age_hours`) and injects `--locked` whenever a `Cargo.lock` is present, so a build can never silently change dependency resolution.

  **Why an age gate works on this threat.** Registry compromises of this class are caught and yanked within hours — in the 2026-08-20 crates.io incident, `arrayref`, `internment` and `append-only-vec` were poisoned for 86, 90 and 107 minutes respectively. A window of 24h or more makes that class unresolvable.

  **Why transitive dependencies matter more than direct ones.** A caret requirement resolves to the newest match: `blake3` required `arrayref ^0.3.5`, i.e. `>=0.3.5, <0.4.0`, which the malicious `0.3.10` satisfied. Projects picked it up without naming arrayref anywhere in their own manifest.

  **What `--locked` does and does not cover.** Cargo respects an existing pin by default, so `--locked` does not protect an unchanged lockfile — it constrains the case where cargo *would* change the graph, turning a silently added dependency into `error: cannot update the lock file`. Anything that re-resolves — no lockfile, `cargo update`, CI without a committed lock, a manifest change — takes the newest published version. Rust **libraries conventionally do not commit `Cargo.lock`**, so they re-resolve on every build.

  Neither control helps a project that has no lockfile *and* no cooldown backend installed; `supply-chain-verify` reports that state as `GAP` (and as `WEAK` when a `Cargo.lock` is present, since `--locked` then protects that lockfile and nothing else).

  **Cargo's own gate (cargo ≥ 1.100.0) is not written yet.** Cargo 1.100.0 (stable 2026-11-12) added a native publish-age gate: `registry.global-min-publish-age` in `config.toml`, or `CARGO_REGISTRY_GLOBAL_MIN_PUBLISH_AGE`. MEASURED on cargo 1.100.0: `global-min-publish-age = "48 hours"` in `$CARGO_HOME/config.toml` made `cargo generate-lockfile` lock the previous release of a crate published a minute earlier; cargo 1.99 warns and ignores the key. The role does not write it yet (planned), so everything below comes from the wrapper, and on cargo ≥ 1.100 a caller that skips the wrapper (`cargo-real`, the rustup toolchain binary) gets no age gate. Measured behaviour to plan around: the native gate acts only when cargo resolves (`cargo build` keeps an existing lockfile, `cargo update` moves to older versions), `"7d"` is a hard error while `"7 days"` works, and an exact pin to a too-new version fails with rc=101 unless `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow` is set.

  **Cargo coverage map.** Each row verified by execution. "Gated" means the publish-age gate evaluates the version before any `build.rs` can run. "Covered" means covered through the cargo PATH wrapper.

  | How a crate version reaches your build | Covered? | By what |
  |---|---|---|
  | Fresh resolution (`build`/`check`/`test`/`run`/`update`) | Yes | age gate via `cargo cooldown` |
  | `cargo update` | Yes | routed through `cargo cooldown` — the one resolution path `--locked` cannot cover |
  | `add` / `generate-lockfile` / `vendor` | **No** | warned, not gated — see below |
  | `cargo install <crate>` | **No** | `--locked` only; warned, not age-gated |
  | A `Cargo.lock` **this host** wrote | Yes | gated when it was written |
  | A `Cargo.lock` from a clone/PR, crate **known-malicious** | Yes | Socket Firewall blocks the download |
  | A `Cargo.lock` from a clone/PR, crate **fresh and unflagged** | **No** | needs a lockfile-age check in CI (not built) |
  | `cargo install --git` / `--path` | **No** | no registry publish date exists to gate on |
  | git / path dependencies, `[patch]`, `[replace]` | **No** | same; needs a `cargo-deny` source allowlist |
  | Vendored crates committed to the repo | **No** | nothing is downloaded or resolved |
  | `build.rs` network egress once any build runs | **No** | structural; needs build-time network isolation |

  The last four are not oversights, they are the shape of the problem. The age gate rests on crates.io recording a publish timestamp server-side; a git ref has no publish event, and a commit date is attacker-controlled via `GIT_COMMITTER_DATE`. `[patch]`/`[replace]` redirect a dependency to such a source, and can be set from a repo-local `.cargo/config.toml`. The countermeasure is a source allowlist — `cargo-deny`'s `[sources]` with `unknown-git = "deny"` — run in your own project's CI. The role does not ship or run it: it operates on a resolved dependency graph (a Rust project), which a host-hardening role has none of, and `cargo deny` is itself unsafe to run on an untrusted repo because it invokes cargo. It is defence-in-depth against git/alt-registry sources, not against the version-compromise the age gate handles.

  And the age gate is admission control, not a sandbox. Once any build script runs it is arbitrary code with your privileges: proc-macro1's `build.rs` connected directly to an IP with certificate validation disabled and executed what it downloaded, with no package manager involved. So the gate counters the attacker who publishes malware and is caught within hours — which is most registry attacks, because scanning is fast — and does nothing against one who publishes benign code and waits out the window. Build-time network isolation (`cargo fetch` online, then `cargo build --offline` with no egress) is the control for that, and cargo cannot provide it.

  **Version floor — the gate is unavailable on stock LTS.** `cargo-cooldown 0.3.5` (the version the role and the action pin; 0.4.x needs rustc 1.97) requires **rustc >= 1.91.1**. Ubuntu 24.04's apt cargo is 1.75.0 and Debian 12's is older still, so on a host using distro cargo the backend cannot be installed and the age gate does not apply — the wrapper degrades to `--locked` and warns on every invocation, and the run summary records the gap. Measured on `ubuntu:24.04`: `error: cannot install package cargo-cooldown 0.3.4, it requires rustc 1.91.1 or newer`. Hosts using rustup (the common case for Rust development) are unaffected. This is the same shape as the npm age gate needing npm >= 11.10.0 against noble's 9.2.0.

  **Socket Firewall for cargo** (`cargo_socket_firewall`, default on) covers the axis the age gate cannot: it filters the *download* rather than the resolution, so it applies to a lockfile written anywhere, and it never participates in version selection — your lockfile is still authoritative. It needs **Node >= 20** like the npm path. What it does when something fails, MEASURED with sfw 2.0.6 and the sfw-free 1.16.0 binary it downloaded (2026-11-19), for cargo and npm alike:
  - **Socket's API unreachable, registry reachable** (its hosts refused, or blackholed): **it fails closed.** The download fails and so does the command: `cargo fetch` exit 101, `npm install` exit 1 (`ECONNRESET`, after about 70 s of npm retries), and sfw's report says it hit a connection error. sfw-free's `SFW_FAIL_ACTION` (`allow` by default, or `block`) made no difference here; what it does govern was not measured.
  - **No network at all:** nothing is downloaded, so only what is already cached builds (a cached crate and a cached npm package both installed, exit 0), and everything else fails as it would without sfw. That is also the limit of the filter: a crate or package served from a local cache is never checked.
  - **GitHub unreachable during sfw's own update check:** it keeps running the binary it has cached, exit 0.
  - **No binary cached** (first use, or after a root `npm install -g` of sfw, which replaces the package directory and the cache with it: MEASURED reinstalling 2.0.6 over itself): sfw downloads it, and fails closed (exit 1) if it cannot. Which binary to download it asks the GitHub API, unauthenticated and with no way to give it a token: 60 calls an hour per IP, shared by everyone behind the same address. MEASURED 2026-11-23: 10 of 30 of this repo's own smoke jobs started with it used up, and with that API answering 403 sfw exits 1 within 0.3 s. So an apply that finds sfw with nothing cached first puts a pinned release there (`sfw_binary_version`, from its download URL, no API call), and only after its SHA-256 matches the pin. A download that does not match is refused: sfw is moved aside and does not get to fetch one itself, because it would accept whatever the GitHub API lists. If the pin cannot be used for another reason, sfw does its own download as before and the run summary says why. If that fails too the role moves sfw aside, so the wrappers pass through with a warning rather than break; `supply-chain-verify` reports that state as `GAP`, never `OK`. A non-root caller cannot do the download at all (sfw's cache is root-owned), so when the cache is empty the npm and cargo wrappers warn by name, run the tool unfiltered, and say to re-apply or run `sudo sh -c 'umask 022; sfw true && chmod -R go+rX <cache>'` once. A bare `sudo sfw true` is not enough wherever sudo runs the command under a umask of 077 (a caller's umask of 077 carries through sudo on Debian 13, as does sudoers `Defaults umask=0077` anywhere; on Ubuntu 24.04 a caller's 077 came out as 022): MEASURED, it left the binary in a 0700 cache that every other account still could not run.
  - **Non-root callers and the hourly update check.** By default sfw rewrites a timestamp in its cache (`.sfw-cache/next-check`) once its last update check is an hour old, and treats a failed write as fatal. Role v2.0.0 worked around that by handing the cache to the deploying user. MEASURED with that approach (main after v2.0.0, before this fix): on NodeSource hosts it missed the real cache, so every non-root npm and cargo call failed one hour after each apply; on Debian's npm every non-root account except the deploying user failed the same way, and the deploying user owned the binary that root runs. The cache is root-owned again (a re-apply resets one an earlier version left writable), the wrappers run sfw with `SFW_SKIP_UPDATE_CHECK=1`, which reads the cache without writing it (MEASURED: no file under it changed), and the update check runs as root, at apply time and from `supply-chain-age-gate-refresh --sfw` on the refresh timer. The one apply that puts the pinned binary in place skips it, so the host's first install is the pin; from an hour later, as after sfw's own download, the timer or an apply moves the host to the current release. A pin is never put over a binary sfw has cached, so bumping `sfw_binary_version` does not reach a host that has one. Anything that empties the cache does bring the pin back: a root reinstall of sfw (an `sfw_version` bump is one) or a reset of a cache another account could write. Until the timer's next run such a host runs the pinned release, which can be older than the one it had. And when the download does not match the pin, the fallback is sfw's own download, whose digest comes from the same GitHub release: a release replaced upstream, API digest included, is refused as the pin and accepted as sfw's. Running `sfw` by hand as a non-root user still hits the hourly failure unless you set that variable.
  - **This needs sfw 2.0.6 or later.** No earlier release reads `SFW_SKIP_UPDATE_CHECK` (checked in every published tarball: 1.0.0 and 2.0.1 to 2.0.4; there is no 2.0.5). Role releases before v2.0.0 installed a floating `sfw@2`, which was 2.0.4 until 2026-05-22, and later releases installed sfw only when it was absent, so those hosts kept 2.0.4 (MEASURED: with 2.0.4 left in place, the read-only wrappers did not help; every non-root npm and cargo call failed an hour after the apply, and a second apply did not repair it). A re-apply now replaces an sfw older than 2.0.6 with `sfw_version`, and installs `sfw_version` over an sfw of any other version too, so bumping or lowering the pin reaches a host that already has sfw (a pin below 2.0.6 never replaces a 2.0.6+ sfw, and a dist-tag or range such as `latest` never replaces a working one: the role cannot tell whether it already satisfies the pin). If that install fails and the old sfw still runs (MEASURED: npm left it untouched when `sfw_version` named a release that does not exist), the run summary names it as still in use rather than as a missing protection. The replacement goes where the sfw root runs is installed, not to root's npm's own prefix: MEASURED on a host whose sfw 2.0.4 came from Ubuntu's npm (prefix /usr/local) and whose npm is now NodeSource's (prefix /usr), installing to npm's prefix left the 2.0.4 first on root's PATH, and that apply moved it aside instead of using the new copy. If that fails, or `sfw_version` is itself older than 2.0.6, sfw is moved aside and listed in the run summary, and npm and cargo run unfiltered rather than fail.

  **The wrapper is a first-invocation control, not an enforcement boundary.** Three mechanisms route around it and none can be closed from a PATH shim: cargo overwrites `$CARGO` with its own resolved toolchain path, so build scripts and third-party subcommands that re-enter cargo do so unwrapped; a repo-local `rust-toolchain.toml` with `path =` supplies its own cargo; and `RUSTC_WRAPPER` or a repo-local `.cargo/config.toml` execute code with no registry involvement at all. It raises the floor for ordinary invocations. Containment of `build.rs` is a separate concern this role does not address: no config-level control exists for it, and constraining what an admitted build script can *do* requires process isolation (a seccomp/Landlock sandbox, a container with no egress, or an ephemeral builder), which is outside what a package-manager hardening role can provide.

  **Unknown subcommands are warned about, not gated.** The set of cargo subcommands is open (any `cargo-*` on `PATH`, plus repo-local `[alias]`), so enumerating it cannot converge. `cargo nextest run`, `cargo watch -x check` and the like pass through with a note on stderr and receive no injected flags — injecting `--locked` into a subcommand that does not accept it would break the build.

  **Opening an untrusted Rust repo can execute its code before you build anything.** A repo-local `.cargo/config.toml` can set `[build] rustc-wrapper`, `[build] runner`, `[target.*] linker` or `[alias]`, and a `rust-toolchain.toml` can point `path =` at a cargo the repo ships. MEASURED: with a repo-local `rustc-wrapper` set, `cargo metadata` executed it — and `cargo metadata` is what rust-analyzer and every Rust IDE run on folder open. `cargo tree` executes it too. So this is not "you accepted the risk when you ran `cargo build`"; cloning and opening in an editor is sufficient.

  Nothing in this role closes it, and a detector would not: `RUSTC_WRAPPER` works as an environment variable with no file to grep, `cargo --config` accepts a file path so a key denylist does not cover it, and `rust-toolchain.toml path=` bypasses the PATH wrapper before it can act. The mitigation is procedural — **inspect `.cargo/config.toml` and `rust-toolchain.toml` before opening a Rust repo you do not trust, or open it inside a container.**

  **A shared cargo cache is a code-injection path that every control here misses.** Cargo verifies a `.crate` checksum when it downloads, but **not** when it reads one already in `~/.cargo/registry/cache` — a repacked tarball whose SHA-256 matches nothing compiles silently under `--locked`, online and offline (reproduced twice). `--locked`, the lockfile checksum, the publish-age gate and Socket Firewall all miss it simultaneously, because none of them re-hash bytes on disk.

  This is not an initial-access vector — writing to the cache requires code execution already. It is a **trust-boundary crossing**: an untrusted build poisons the cache, and a later privileged build compiles the result. Two concrete routes:

  - **Self-hosted runners with a persistent `~/.cargo`** — a malicious PR's `build.rs` runs in a low-privilege job and the next job inherits the cache.
  - **GitHub-hosted runners using `actions/cache`** — cache scoping normally isolates branches, but `pull_request_target` runs in the *default branch* context. Until June 2026 that let it write the default-branch cache scope, and job `permissions` blocks did not apply to cache writes at all. That is how Angular (2024) and TanStack (2026) were compromised. [GitHub then made that cache read-only](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/) for triggers a non-collaborator can fire (`pull_request_target`, `issue_comment`, fork-PR `workflow_run` cascades), and [`pull_request_target` itself is blocked by default on public repositories from 2 December 2026](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2). Neither reaches GitHub Enterprise Server, and neither covers a self-hosted runner's persistent cache above. The changelog does not say whether the read-only cache applies to private repositories, so do not assume it.

  **This role cannot close it.** It runs at provision time; the poisoning happens between builds. A verify-time check would report coverage it does not have. The fix is topological — do not share a cargo cache across trust boundaries, and do not restore an untrusted cache into a privileged job. If you must, purge `~/.cargo/registry/cache` rather than trusting it, or verify cached `.crate` files against a committed `Cargo.lock` or `index.crates.io` (both independent of the local sparse index, which an attacker with cache write access also controls).

  **Known boundaries of the cargo gate**, each verified by execution:

  - **A `Cargo.lock` you did not generate is trusted.** `lockfile-baseline = "floor"` accepts versions an existing lockfile already pins, so a branch or PR that ships its own lockfile pinning a fresh crate will build. This is not a regression — stock cargo trusts lockfiles unconditionally and applies no age check at all — but it means **reviewing lockfile diffs in PRs is load-bearing**, exactly as the crates.io advisory recommends. `cargo update` is routed through the gate; the other lockfile-writing commands (`add`, `generate-lockfile`, `vendor`) are warned about rather than gated. An earlier version reverted them by copying `Cargo.toml`/`Cargo.lock` aside and restoring on refusal — that was removed as an unacceptable shape for a hardening role to impose on a user's source tree.
  - **A `cooldown.toml` committed to the repo can still loosen the gate.** The wrapper pins cargo-cooldown's environment layer, which beats every `cooldown.toml` for the settings that have an environment form: the global and crates.io windows, the clock (`now`), `skip_registries`, the violation action and the lockfile baseline. MEASURED on cargo-cooldown 0.3.5: a repo file setting `[registry] min-publish-age = "0"`, `now = "2099-…"` or `skip_registries = ["crates-io"]` is overridden. But `[allow.global] minutes`, `[[allow.package]]`, `[[allow.exact]]` and `[registries.<alt>] min-publish-age` have no environment form, so a repo file can still use them: `[allow.global] minutes = 0` built a crate published hours earlier. `supply-chain-verify` reports any `cooldown.toml` between the working directory and `$CARGO_HOME` as `GAP`. Treat one in an untrusted repo as a bypass. The crates.io window is pinned through `CARGO_REGISTRY_MIN_PUBLISH_AGE`, a variable cargo-cooldown reads. Side effect of the pin on cargo 1.99: cargo also reads it as its own unstable setting and prints `warning: ignoring registry.min-publish-age without -Zmin-publish-age` on each routed build. Cargo 1.100.0 stabilised the setting under another name and ignores `CARGO_REGISTRY_MIN_PUBLISH_AGE` without a word (MEASURED on cargo 1.100.0: set alone it neither gated plain `cargo generate-lockfile` nor printed anything), so the variable does not hand the wrapper's window to cargo itself. Cargo's own gate reads `CARGO_REGISTRY_GLOBAL_MIN_PUBLISH_AGE` (`registry.global-min-publish-age`) and `[registries.crates-io] min-publish-age`.
  - **`SUPPLY_CHAIN_CARGO_WRAPPED=1` disables the wrapper** for that invocation. It exists to break the cooldown→cargo→cooldown recursion and cannot simply be removed. It is also inherited by build scripts, so a nested `cargo` call from a `build.rs` is unguarded — though a build script already has arbitrary execution by then.
  - **Only the discovered cargo path is wrapped.** The rustup toolchain binary (`~/.rustup/toolchains/*/bin/cargo`) and `cargo-real` remain directly callable, as with every other wrapper in this role. `supply-chain-verify` reports `not deployed` when `command -v cargo` resolves somewhere unwrapped.

  See [TESTS.md](../TESTS.md) for details.
- **Cross-version coverage is narrower than the tiering implies.** The composer version tiers (`< 2.7`, `2.7–2.8`, `>= 2.9`) were measured by hand across composer 2.0.14 → 2.10.3 and are locked in by rendering tests (`tests/bats/28-composer-tier-rendering.bats`), but CI runs the *behavioural* composer tests against a single current composer. What CI does run across versions: a stock-distro apply-and-verify matrix (`.github/workflows/coverage-matrix.yml`: Ubuntu 22.04 / 24.04 / 26.04, Debian 12), a Node 20 / 22 / 24 matrix that covers pnpm 10 and 11, and a non-root + interactive apply (`.github/workflows/nonroot-interactive-apply.yml`) — the cell where every Aug 2026 bug lived. Not verified anywhere: other ecosystems' version axes (npm × node, pip × python — same bug class likely), composer self-update interaction, `php composer.phar` invocation, a second non-deploying user on the host, and pam_env / systemd-unit behaviours that need a real systemd host rather than a container. See [TESTS.md](../TESTS.md) → "Known coverage gaps" for the full list.
- **Composer script blocking is layered.** Composer has no host-wide config-file or env-var mechanism for disabling scripts — `COMPOSER_NO_SCRIPTS` and `"scripts-are-disabled": true` are not real composer concepts (composer ignores them). The role ships two layers: (1) a wrapper at the path composer was found (`/usr/local/bin/composer` for the upstream installer, `/usr/bin/composer` for the distro package), with the real binary moved next to it as `composer-real` (`/usr/local/bin/composer-real` or `/usr/bin/composer-real`). It injects `--no-plugins` on every invocation and `--no-scripts` on every invocation except a script you ask for by name; (2) `COMPOSER_SKIP_SCRIPTS=<full event enumeration>` in `/etc/profile.d/` and `/etc/environment` catches `php composer.phar` callers and `composer-real` callers in PAM-loaded shells on composer ≥ 2.8.6 (measured: ignored on 2.2.6, 2.7.1, 2.8.4 and 2.8.5, honoured from 2.8.6). Below composer 2.2.0 `--no-scripts` is not an application-level option — only `install`, `update`, `require`, `remove`, `dump-autoload`, `create-project` and (2.1) `reinstall` accept it there (measured with `composer list --format=json` on 2.1.14, and `help` on 2.0.14), and injecting it anywhere else makes `composer show`/`config`/`diagnose` fail — so on those hosts the wrapper gates the injection to those commands, under any alias or unique prefix composer would resolve to them (measured on 2.1.14: when only the full names got it, `composer req`, `upd`, `ins`, `dump` and `rem` ran the root update and autoload-dump scripts), and the run summary records the gap. The documented per-invocation bypass for both layers is `COMPOSER_SKIP_SCRIPTS= <wrapper path>-real install` (for example `/usr/bin/composer-real` on an apt host) — clearing the env var and going around the wrapper. On composer ≥ 2.8.6 `composer-real install` alone is still blocked by the env-var layer, which is intentional; below 2.8.6 that layer is inert and going around the wrapper is by itself enough. Disable the wrapper layer entirely with `composer_path_wrapper=false` (restores the real binary at the wrap location on next apply; env-var layer remains active).
- **A composer script you name still runs; lifecycle scripts do not.** Composer only runs scripts from the root `composer.json`, never a dependency's (dependency code reaches composer through plugins, which `--no-plugins` and `allow-plugins` block). The wrapper therefore treats the two ways a root script runs differently, the same line npm draws under `ignore-scripts`: lifecycle events (`post-install-cmd`, `post-update-cmd`, `post-autoload-dump`, `post-create-project-cmd`, `pre-command-run`, …) fire as a side effect of `install`, `update`, `require` and the rest, and get `--no-scripts`; `composer run-script <name>`, `composer run <name>` and `composer <name>` for a name under `"scripts"` (or one of its `"scripts-aliases"`) are explicit, and get none. Before this, `--no-scripts` on an explicit run did not refuse it, it emptied it: measured on composer 2.2.6, 2.5.5, 2.7.1, 2.8.8, 2.9.5 and 2.11.2, `composer test` exited 0 having run nothing, and `composer run-script test` said `Script "test" is not defined in this package`. A name counts as a script only when composer itself would run it as one: it is in the `composer.json` composer reads (`-d`/`--working-dir`, `$COMPOSER`, the parent-directory walk) and is not a built-in command or a script event name, so a checkout that defines a script called `install` still gets `composer install --no-scripts` (composer refuses to let a script shadow a built-in). A name that is a script and also another spelling of a built-in is refused, with a `[supply-chain-hardening] refusing` message that names `composer run-script <name>`. Composer resolves an exact command name before it expands a unique prefix of a built-in, and a script is a command: measured on 2.7.1 and 2.11.2, a checkout defining scripts named `req`, `du`, `dump`, `up`, `upd`, `ins` or `rem` had them run, with scripts enabled, on `composer req psr/log` and the rest, and a `"scripts-aliases"` alias `i` or `upgrade` ran its script in place of that built-in. An ordinary project script whose name is a prefix of a built-in is refused the same way, for example `check` (`check-platform-reqs`): run it as `composer run-script check`. The wrapper's list of built-ins is fixed (every command of composer 2.1.14 through 2.11.2), so a built-in that a later composer adds is not recognised until the list is updated. Four limits: an abbreviation of a script name (`composer tes` for `test`) and a script of the global `composer.json` (`composer global <script>`) are not recognised, so they still get `--no-scripts` and exit 0 having run nothing (measured on 2.11.2) — name the script in full, from the project; a script that itself calls `@composer …` runs that nested composer as `composer-real`, without the wrapper's flags, so neither `--no-scripts` nor `--no-plugins` applies inside it: measured on 2.11.2, a script `"@composer update"` run by name activated a plugin the project's `allow-plugins` enables, and that plugin can be dependency code; and on composer ≥ 2.8.6 `composer run-script post-install-cmd` (a lifecycle event run by hand) is refused by the `COMPOSER_SKIP_SCRIPTS` layer with composer's own `Script "post-install-cmd" is not defined` message. Clear the variable for that one step: `COMPOSER_SKIP_SCRIPTS= composer run-script post-install-cmd`.
- **Reinstalling or upgrading the composer package removes the wrapper.** The wrapper replaces the file at the path the package manager owns, so `apt-get install --reinstall composer` (or an upgrade) writes the stock `/usr/bin/composer` back over it. Measured on Ubuntu 24.04's composer 2.7.1: after the reinstall `/usr/bin/composer` was the stock file again, a lifecycle script ran through it, and `supply-chain-verify` reported `GAP` on both `composer PATH wrapper` and `composer lifecycle scripts blocked`; re-applying the role wrapped it again and both rows went back to `OK`. The same holds on an upstream install for anything that writes a new `composer.phar` to `/usr/local/bin/composer`, such as re-running the installer. `composer self-update` does not: it replaces the file it runs from, which is `composer-real`, and the wrapper survives (measured, 2.8.8 to 2.9.5 through the wrapper: the wrapper was unchanged and both rows stayed `OK`). Re-apply after any composer upgrade either way, so the version-tiered settings follow the new version. (`dpkg-divert` would keep the distro package's own file out of the way and make the wrapper survive package operations; the role does not do that yet.)
- **Composer audit blocking is version-tiered.** The role detects the installed Composer version and renders the strictest config that version supports. `audit.block-insecure` and `audit.block-abandoned` (which actively refuse updates to packages with known advisories) require Composer ≥ 2.9 (released 2025-11). `audit.abandoned: fail` requires ≥ 2.7. Distro-shipped versions hit different tiers: Ubuntu 24.04 noble ships 2.7.1 (gets `abandoned` but not `block-*`), Ubuntu 22.04 jammy ships 2.2.6 and Debian 12 bookworm ships 2.5.5 (neither gets the `audit` block at all). When Composer isn't installed at apply time, the safe baseline is written — re-run the role after `apt install composer` (or the upstream installer) to upgrade the config to the version-appropriate tier. The baseline hardening (`secure-http`, `allow-plugins`, `preferred-install: dist`) applies on every tier and every supported platform. `allow-plugins` is written as the empty allowlist `{}`, on every version, unless `composer_allow_plugins` is true (both writers then write `true` and the wrapper drops `--no-plugins`): the literal `false` is a hard fatal on composer < 2.2.15 (`array_merge(): Argument #1 must be of type array, false given`, exit 255 on every command but `--version`) — which is exactly the composer Ubuntu 22.04 ships — and the fix was not backported linearly (2.3.0 through 2.3.7 fatal too), so no version predicate is safe. `{}` is accepted everywhere and denies every plugin a project has not listed (an error in a non-interactive run, a prompt in an interactive one). Composer also reports `{}` as no value at all, since it is its own default; `supply-chain-verify` reads "no allowed plugin" as the hardened state.
- **`harden.sh --home-only` covers only what a file under HOME can carry.** It writes no `/etc` file and no env file, wraps only a tool that is itself under HOME, and leaves a wrapper an earlier full apply put elsewhere as it is, not updated. So on an agent's VM whose tools are in the image: deno has no age gate, bun and bunx can fetch and run a package with no gate, composer runs `composer.json` scripts, and cargo gets no `--locked`; `COMPOSER_SKIP_SCRIPTS` and `DOTNET_NUGET_SIGNATURE_VERIFICATION`, which exist only as variables, apply nowhere, so on the Mac measured NuGet checked no package signature (SDK 10.0.106, 2026-11-27: there `signatureValidationMode=require` is enforced only with the variable set); Gradle and Maven get nothing when HOME is not the passwd home; other accounts get nothing; and a tool too old for a setting (npm 10.9.4 and pip 24.0 on the VM measured on 2026-11-26) stays ungated, since only the image can upgrade it. Anything outside HOME has to come from the image anyway on a VM like the first one measured on 2026-11-26/27, where files in `/root`, `/usr/local/bin` and `/etc` did not survive a redeploy and HOME did. Its summary lists what applies to the host it ran on under "Not reachable from HOME".
- **Socket Firewall requires Node >= 20.** On older Node versions, sfw is not installed.
- **npq requires Node >= 20.13.0, and fails OPEN below it.** npq is the reputation layer — the one that addresses slopsquatting, where an attacker pre-registers a plausible package name an agent might guess. An age gate does nothing against a squat registered months ago; reputation is what catches it. On Node < 20.13.0 npq prints `npq suppressed due to old node version` to stderr, passes the command through to the real package manager, and **exits 0** — so it is on `$PATH`, returns success, and checks nothing. Note this floor is *not* the one in npq's `package.json` (`engines.node >= 24.0.0`); the runtime gate in `lib/helpers/cliSupportHandler.js` is `>=20.13.0`, and it is identical in 3.19.6 and 3.23.3, so pinning an older npq does not rescue an older Node. The role therefore gates the install on the runtime threshold, verifies after installing that npq is not suppressed, removes the `/etc/profile.d/npq-aliases.sh` aliases when it is, and reports the gap in the end-of-run coverage summary. Combined with sfw's Node >= 20 floor, a host below Node 20 keeps the config-file hardening but has **no reputation layer at all** — see "What this does not do" about which threats that leaves open.
- **Container image hardening requires podman, and is opt-in.** Docker has no daemon-level policy enforcement. When `podman_enabled=true`, the playbook installs podman with `policy.json` registry restrictions; disabling the Docker daemon is a **separate** gate (`podman_disable_docker=true`). Both default to `false`, so a default run neither installs podman nor touches Docker.

- **`--check` (dry run) is supported, and its detection probes really run.** Ansible does not execute `command`/`shell` tasks under `--check`, so every read-only probe in this role carries `check_mode: false`. Without it the registrations came back empty, every downstream `when:` gate evaluated against nothing, and a dry run both hard-aborted at the pre-flight GNU-date probe *and* reported deployed protections (npm/pip wrappers, npq, the bun/deno/composer wrappers) as skipped — while printing a coverage summary built from the same empty values, e.g. `found Node .` with no version. A dry run that misreports coverage is worse than no dry run, since vetting a hardening role before production is exactly what `--check` is for. The probes are all `changed_when: false`, so forcing them to run changes nothing the role manages. They do run the tools, which write their own caches and logs: MEASURED 2026-11-23 in the test image (already hardened, Node 22), a full `--check` run reported `changed=0` and left npm logs under `~/.npm/_logs`, uv cache and lock files, a Go telemetry counter, node compile caches in `/tmp` and `~/.ansible`. For a preview that changes no file, use `action/harden.sh --preflight` (MEASURED the same way: nothing on the filesystem changed but the test's own output). A non-root run of it makes one `sudo -n true` probe, which sudo logs. Residual caveat: `--check` still cannot show the *contents* a template would render on a host where the tool is absent, so treat a check-mode diff as a plan, not a byte-level preview.

- **Do not run the role with global `--become` / `sudo ansible-playbook`.** Facts are gathered under the play's become settings, so escalating from a non-root account sets `ansible_facts.env.HOME=/root` and every per-user config lands in root's home instead of the intended user's. The role escalates per task where root is required, so plain `ansible-playbook site.yml` still applies all system-wide hardening. Pre-flight refuses this invocation; override with `-e accept_root_home_targeting=true` if you really do mean to harden root's home.

- **Podman hardening is registry-allowlisting, not image-signature enforcement.** When `podman_enabled: true`, the deployed `/etc/containers/policy.json` rejects any registry not on `podman_allowed_registries` (good), but maps each *allowed* registry to `insecureAcceptAnything` — every image from an allowed registry (docker.io, ghcr.io, …) is pulled **without signature verification**. cosign is installed for *manual* verification only; it is not wired into the policy (there is no `sigstoreSigned`/`signedBy` rule). So the control bounds *which registries* you pull from, not *which images* — a compromised or typosquatted image on an allowed registry is accepted, and the installed cosign should not be read as signature *enforcement*. This is deliberate: a `sigstoreSigned` policy would break pulls of the many unsigned images on public registries, so it is not a safe default. If you only run signed images from a sigstore/cosign-capable registry, add a `sigstoreSigned` rule for that registry yourself. An opt-in signature-enforcement tier is tracked in ECH-204.
- **Container image pulls have no age gate, on any tool.** The publish-age gates are package-manager settings; `podman pull` and `docker pull` have no equivalent. In the LiteLLM compromise the mutable tags `latest`, `main-latest` and `main-stable` pointed at the malicious image, and Docker Hub was not fixed until about 2.5 hours later, so a host pulling by tag took it with every gate here in place. Pin digests rather than tags.
- **Provenance is evidence, not proof.** LiteLLM's malicious image carried provenance naming the real release workflow with a source repository one hyphen off (`Berri-AI/litellm`), so a check on the builder alone would likely have passed. The same check on source would not have caught TanStack, where the publish came through the real repository's trusted-publisher binding. Any signature tier should pin the source repository as well as the builder, and neither replaces the age gate.

## Complementary hardening (outside this role)

Some defenses against supply-chain attacks live at the application or runtime layer, not the package-manager layer. The role doesn't ship these because the safe configuration is application-specific — defaults that would block real attacks also break legitimate workflows.

### PHP runtime: php.ini `disable_functions`

Composer's `autoload.files` mechanism executes helper code on every PHP request that includes `vendor/autoload.php`. This path is **independent of install scripts** and **unaffected by `--no-scripts`, `COMPOSER_SKIP_SCRIPTS`, or `audit.block-insecure`**. The Laravel-Lang compromise (May 2026, 700+ retagged versions) used this exact path: the malicious `src/helpers.php` ran on every request and called `exec()` to fetch a second-stage payload from a C2 server.

The runtime mitigation is `disable_functions` in `php.ini`:

```
disable_functions = system,passthru,shell_exec,pcntl_exec
```

This neuters the most common subprocess-execution paths.

**This role doesn't ship this** because there is no host-wide safe default. Disabling `proc_open` breaks Composer itself (Composer uses `proc_open` to invoke git, gpg, and gh). Disabling `exec` breaks many composer plugins and Symfony Process. The "safe" subset is application-specific: a host running a Symfony app may need `shell_exec`; a host running only API workers usually doesn't. This decision belongs in the user's php.ini deployment, not a default-applied Ansible role.

**Recommendation:** if you control the PHP applications on the host, add a conservative `disable_functions` set to your own php.ini management. Start with the four functions above, run your normal application workflows, and expand the list only after confirming each addition is actually unused.


### Python runtime: interpreter startup hooks (`.pth` / `sitecustomize.py`)

A wheel's `<dist>-<version>.data/purelib/` section is unpacked to the **site-packages root**, not under the package's own directory. Python's `site` module then **executes** any line in a `*.pth` file beginning with `import`, and imports `sitecustomize` — both on **every interpreter start**, before any of your code, with no import of the package required. The October 2026 litellm compromise used exactly this: `cook.pth`, `cook.py` and `sitecustomize.py` shipped in the wheel's `.data/purelib/`, firing on `pip`, `pytest`, a Jupyter kernel, or a bare `python -c "pass"`. The sdist did not carry the payload, but it was not clean either: its `pyproject.toml` added `data = "cook"`, which is not in the Git tag. So reading the source showed nothing, and only a diff against the tag would have.

This path is **independent of install scripts** and unaffected by every mechanism-specific Python control this role deploys — `only-binary = :all:` and uv's `no-build` both target `setup.py` execution from an sdist, and a wheel never runs code at install time at all. It is the Python analogue of Composer's `autoload.files` above.

MEASURED on cpython 3.13.12, with a `.pth` planted in site-packages:

| invocation | `.pth` executed? |
|---|---|
| `python3 -c "pass"` | yes |
| `python3 -I` (isolated mode) | yes |
| `python3 -s` | yes |
| `PYTHONNOUSERSITE=1` | yes |
| `python3 -S` | no |

`-I` is the trap: "isolated mode" implies `-E -P -s`, none of which touch `.pth` processing in the main site-packages. `-P` / `PYTHONSAFEPATH` — the role's `python_safe_path` — governs `sys.path[0]` and is irrelevant to this.

**This role doesn't ship a mitigation** because the only lever is `python3 -S`, and it is unusable: "don't imply `import site`" also means site-packages never joins `sys.path`, so nothing you installed is importable. It is additionally **command-line only** — Python exposes no environment variable and no config file for it, so neither the role's env layer nor its config layer can reach this class at all. Neither `pip install` nor `uv pip install` exposes any option that refuses a wheel carrying such a payload.

**What does cover it:** the publish-age gate, on both the uv and the pip layer, precisely because it is mechanism-independent — it refuses the artifact by upload time without needing to understand what is inside it. The malicious litellm wheels were live for roughly 1h43m against a 48h default window. That covers the paths where a gate applies, not every path: an ungated venv, PDM, and an image pulled by tag would all have taken it (see the venv and container entries).

**Recommendation:** treat "installed but never imported" as executed. For detection rather than admission control, audit the site-packages root for `*.pth`, `sitecustomize.py` and `usercustomize.py`; the legitimate baseline is small and stable — a realistic install of setuptools, wheel, pytest, numpy, pandas, matplotlib and ipython produces exactly two (`distutils-precedence.pth` and `_virtualenv.pth`), neither from an application dependency. `supply-chain-verify` runs this audit before it starts Python normally, reading the files as Python would: lines split where CPython splits them, path lines followed to the directories they add, and `sitecustomize` / `usercustomize` looked for there and on `PYTHONPATH`. A hook with nothing vouching for it becomes a WEAK `python startup hooks` row naming the distribution that installed it, plus a warning on stderr. Two kinds are recognised and listed in an OK row instead: a file a Debian package installed that still matches the checksum dpkg recorded (stock ubuntu-24.04 runners ship one), and a `.pth` whose line is exactly what setuptools, virtualenv/uv or an editable install generates. The second kind is noise reduction, not assurance: the line only imports a module, and a wheel can ship the same line with its own module, which is why those hooks are listed and never dropped. The audit is detection only, removes nothing, and a quiet result is not a clean bill: it reads the site directories it can find, not everything on `sys.path`.
