## Adversarial tests

These simulate real supply chain attack patterns using harmless fixtures. Each fixture performs a "malicious" action (writes a marker file, reads fake credentials, appends a fake SSH key). The test passes if the action was blocked — the marker file doesn't exist, the credentials weren't read, the SSH key wasn't appended.

No actual malware is used. All fixtures are local packages with scripts that write to `/tmp/marker-*` files.

### npm attack simulations

| Test | Attack pattern | Real-world source | Defense |
|---|---|---|---|
| SSH key exfiltration | postinstall reads `~/.ssh/id_rsa` and `~/.ssh/id_ed25519` | BufferZoneCorp (Apr 2026) | `ignore-scripts=true` blocks postinstall |
| Env var harvesting | postinstall dumps vars matching token/key/secret/pass | BufferZoneCorp, LiteLLM (Mar 2026) | `ignore-scripts=true` blocks postinstall |
| SSH persistence | postinstall appends attacker key to `~/.ssh/authorized_keys` | BufferZoneCorp Go modules | `ignore-scripts=true` blocks postinstall |
| Preinstall hook | preinstall writes marker (runs before code is unpacked) | Shai-Hulud npm worm | `ignore-scripts=true` blocks preinstall |
| Install lifecycle hook | install hook writes marker (distinct from pre/post) | event-stream (2018) | `ignore-scripts=true` blocks install |

### Python attack simulations

| Test | Attack pattern | Real-world source | Defense |
|---|---|---|---|
| setup.py credential theft | setup.py reads SSH keys, AWS creds, harvests env vars | LiteLLM/Telnyx (Mar 2026) | uv `no-build=true` refuses to run setup.py |
| setup.py SSH persistence | setup.py appends attacker key to authorized_keys | BufferZoneCorp | uv `no-build=true` refuses to run setup.py |
| pip redirect bypass | calls `/usr/local/bin/pip install` with malicious sdist | any agent using pip directly | pip wrapper routes to uv, no-build blocks it |

### Go environment poisoning simulations

| Test | Attack pattern | Real-world source | Defense |
|---|---|---|---|
| GOSUMDB set to "off" | malicious init() disables checksum verification | BufferZoneCorp CI poisoning | `/etc/profile.d/` re-sets to `sum.golang.org` |
| GOPROXY redirect | malicious init() redirects to attacker proxy | BufferZoneCorp CI poisoning | `/etc/profile.d/` re-sets to official proxy |
| GOPRIVATE wildcard | `GOPRIVATE='*'` marks every module private, skipping sumdb checks | sumdb bypass | `/etc/profile.d/` exports it empty; `/etc/environment` never assigns a value |
| GONOPROXY / GOINSECURE | module fetches skip the proxy, or allow plain HTTP | proxy and TLS bypass | same as GOPRIVATE |
| GOTOOLCHAIN override | malicious code triggers toolchain auto-download | toolchain substitution | `/etc/profile.d/` enforces `local` |
| go.mod `toolchain` directive | a repo's go.mod names a toolchain to fetch and run | toolchain substitution | `GOTOOLCHAIN=local` ignores it |

`GONOSUMDB` is also a real sumdb bypass (BufferZoneCorp set `GONOSUMDB=*`). `/etc/profile.d/` exports it empty, but no test asserts that yet. An earlier version of this table listed a `GONOSUMCHECK` test; that is not a Go variable (0 matches in go1.27.4's `GOROOT/src`, and `go env -w GONOSUMCHECK=1` fails), so there is nothing to defend.

### System-level enforcement tests

| Test | What it verifies |
|---|---|
| /etc/environment permissions | Owned by root, mode 644 — non-root can't modify hardening |
| /etc/profile.d/ permissions | Owned by root, mode 644 — non-root can't modify hardening |
| pip wrapper permissions | Owned by root, mode 755 — non-root can't swap the wrapper |
| Non-interactive npm env vars | `bash -c` gets NPM_CONFIG_IGNORE_SCRIPTS=true |
| Non-interactive Python env vars | `bash -c` gets PYTHONDONTWRITEBYTECODE=1 |
| Non-interactive Go env vars | `bash -c` gets GOSUMDB=sum.golang.org |
| Clean markers | No attack marker files exist after full test run |

## How the test container works

1. **Docker build** installs Ubuntu 24.04 + npm, uv, Go, pnpm, yarn, bun
2. **Ansible runs at build time** — applies the hardening role, bakes it into the image
3. **Fake credentials are planted** — SSH keys, AWS creds in expected paths for exfil tests to target
4. **BATS runs at container start** — executes all tests against the hardened environment

The fixtures (fake npm packages with scripts, Python sdists with setup.py) are copied into the image. The "malicious" scripts write marker files to `/tmp/`. If the hardening works, the markers never get created.

## On real Macs

`.github/workflows/macos.yml` runs the Action on GitHub's macos-15 and macos-15-intel with the real tools. `tests/macos/attacks.sh before` has to see every attack fire on the unhardened machine, and `attacks.sh after` every one blocked, in the words of the control that is meant to block it: an npm dependency's postinstall; a pnpm 10 and a pnpm 11 project postinstall (with the job's environment, and with none) and a release hours old; a trusted Bun dependency's postinstall; an sdist's `setup.py` under uv; a Composer lifecycle script; a stale `Cargo.lock` and a stale `Gemfile.lock`; a go.mod `toolchain` line; a Gradle dynamic version and http repository; a Maven parent POM over http; and an unsigned NuGet package. `normal-use.sh` then runs each tool the ordinary way, and `root-owned.sh` looks for root's files left in HOME. What Maven Central's rate limit kept from running is NOT TESTED: a warning, neither a pass nor a fail.

The same workflow runs the role on a Mac, which has to refuse before it writes anything, and `ci-script.yml` runs `tests/ci` on both Macs and on one set up like a person's (npm 11.5.1, Apple's `bundle`, no JDK, and a sudo that would ask for a password).

## In agent shells

`ci-script.yml`'s `agent-shells` job runs `action/harden.sh --home-only` and the verifier in containers set up like the two agent VMs in [Agent runners](docs/design-principles.md#agent-runners), and builds the shipped [`action/examples/Dockerfile`](action/examples/Dockerfile). [`tests/ci/agent-shell/run.sh`](tests/ci/agent-shell/run.sh) drives each cell. Each first checks what the container really holds, and the postinstall, outside-`HOME`, alias, env-layer, entrypoint and rebuild checks each have a control that shows the check can see the opposite:

- **vm-a**: root with `HOME=/home/hatch`, npm 10.9.4 and bun in a read-only mount ahead on `PATH`, apt's pip 24.0, uv only in `~/.local/bin`, every command through `bash --norc --noprofile -c "umask 0007; ..."`. Two runs change nothing outside `HOME` (`/tmp` and `/root` included) or in the mount, and the second nothing under `HOME` but its record; a dependency's postinstall is blocked; the verifier, from that shell, reports npm's age gate as a GAP at the read-only path, pip's as a GAP, bun's runtime auto-install and bunx as GAPs no re-run of `--home-only` closes, uv's system config and the env layer as N/A, and `--fail-on=config` exits 0.
- **uid-without-passwd**: uid 4242 with no passwd entry and `HOME=/tmp/h` (podman runs it with `--passwd=false`): nothing outside `HOME`, and nothing for Gradle or Maven.
- **replayed-state**: a state saved from `bash -ilc` with no terminal on a host hardened as the example Dockerfile does it, replayed under `expand_aliases`: the env layer is there and no npq alias is, against a state saved in a terminal, whose aliases apply on a later line and not on the line that sources the state.
- **image-recipe**: the example Dockerfile, built as shipped; the verifier, run through its entrypoint, finds no GAP a re-run of the hardening would close; `IMG --version` and `IMG -e` run node, as on the base image; rebuilt with nothing changed it keeps its uv and pip cutoffs, a new `HARDEN_STAMP` gives new ones, and the same stamp again is served from the cache.

## Running tests

```bash
make test          # build container + run all 661 tests
make shell         # drop into the hardened container for manual exploration
make test-dev      # docker-compose with mounted tests for fast iteration
```

**The suite expects to run as root**, as it does in the container (`make test`, and CI's `test.yml`). Run as a normal user on a real host, a test that has to write a root-owned path (`/etc/npmrc`, `/etc/uv`, `/etc/profile.d`), move a root-owned binary aside, or add a user skips with `needs root: <what it writes>` instead of failing with "Permission denied" (`require_root` in `tests/bats/setup.bash`). That includes the whole of `38-preflight-become-guard.bats`, whose `setup_file` adds a user: on the November 2026 VM runs, which were all non-root, it reported a single "setup_file failed" in place of its tests, so they never ran there. In the container suite they run. Tests that need a tool feature skip by capability, not by version guess (for example `pip install --dry-run`, which pip 22.0.2 on Ubuntu 22.04 lacks).

Tests that re-run the full playbook (preflight tests in `25-integration-regressions.bats`, idempotency check) are slow. `SKIP_SLOW=1 make test` skips the idempotency double-apply and the other playbook-running tests in `25-integration-regressions.bats` (check-mode dry run, Go floor, tool pins, end-of-run summary); the preflight tests run regardless.

## Measurement hazards when writing tests

- **`npm config` answers for the directory you are in.** npm reads a project `.npmrc` from its *local prefix*: the nearest ancestor holding a `package.json` **or a `node_modules`**, and — when no ancestor has either — the current directory itself. That file outranks both `~/.npmrc` and `/etc/npmrc`, so any `.npmrc` in or above the working directory can invert a test. MEASURED on npm 10.9.8 in a clean `/tmp` tree with `~/.npmrc` saying `true`: a bare directory holding only `.npmrc` (`false`) read `false`, as did a directory with a `node_modules` and its subdirectory. An earlier version of this note said a bare directory was safe; that measurement was confounded by a `node_modules` higher up the scratch path, which is exactly this hazard. An `NPM_CONFIG_*` env var still wins over the project file. Read npm config from a fresh `mktemp -d` under a path with no `package.json` / `node_modules` ancestors (and strip `NPM_CONFIG_*` when testing a file layer), as `npm_implements` in `templates/verify.sh.j2` does; ECH-187 was a false OK from exactly this.

## Known coverage gaps

These are scenarios the test suite does **not** cover. They're tracked here so a bug fitting one of these patterns doesn't come as a surprise:

- **Stock-go matrix.** Tests run against the Go installed by tarball in `tests/Dockerfile` (currently `GO_VERSION=1.24.2`). They don't exercise the role against Ubuntu 24.04's stock `apt golang-go` (1.22), which is what triggered H3 in the May 2026 review. The structural regression catcher in `25-integration-regressions.bats` covers the *fix* but a future "the toolchain requirement crept up again" wouldn't fail. Adding a `GO_FROM_APT=1` Docker build mode and a matrix entry would close this.
- **Fresh-host PATH simulation — partially closed.** The Docker image prepends `~/.local/bin` to `PATH`, masking the bare-`uv` failure mode (H1/H2). `25-integration-regressions.bats` simulates the stripped-PATH case with `env -i` for direct binary calls, and `48-caller-context-coverage.bats` now asserts the general class — that coverage depends on what the bare command resolves to in the caller's shell, measured with the run-probe rather than inferred from PATH position. **This gap was scoped to one tool and should have been read as a class:** the same failure mode let an activated virtualenv bypass the pip wrapper undetected until 2026-10-21, and `docs/limitations.md` had already described it for mise/asdf/volta shims. What is still NOT covered: re-running `ansible-playbook` itself under a stripped PATH, and the caller contexts 48-* skips when their toolchain is absent — notably rustup's `~/.cargo/bin` (its default install dir, which the role's own wrapper discovery depends on), the bun/deno official installer prefixes, a tool installed *after* the apply (the role can only wrap what it found), and the login-vs-non-login split in which the apply's own final verify runs.
- **pnpm 10 vs pnpm 11 matrix — partially closed.** The CI Node matrix now exercises both: Node 20 pins pnpm@10 (pnpm 11 requires Node >= 22), Node 22/24 get pnpm 11. That split is what surfaced `block-exotic-subdeps` being inert on pnpm 10. Remaining gap: the pnpm version is a side effect of the Node version rather than an independent axis, so "pnpm 11 on Node 24" and "pnpm 10 on Node 24" are not both tested. Version-sensitive behavioral tests should gate on `pnpm --version` (see the `block-exotic-subdeps` test in `13-pnpm-adversarial.bats`) rather than assume the container's pnpm.
- **Non-corepack environments.** pnpm/yarn are installed via corepack; on hosts without corepack (apt npm 9 on Node 18 — common on stock Ubuntu 20.04/22.04), the role's pnpm/yarn tasks would behave differently. Not currently tested.
- **Cache-time bypass under adversarial conditions.** `27-cache-and-time.bats` documents the gap (pre-poisoned `~/.npm/_cacache` may bypass the age gate) but doesn't actually populate a malicious cache and demonstrate the bypass. Would require a fixture with a known-recent publish timestamp; brittle in CI.
- **Clock-skew bypass.** `27-cache-and-time.bats` notes the gap but skips the actual exploit without `faketime` installed. Adding `faketime` to the Dockerfile and writing the test would lock in the documented behavior.
- **`python3 -m pip --no-binary :all:` defense.** Tested as a documented bypass that succeeds (test #4 in `09-python-adversarial.bats`). No defense is in place; the test pins this so a future "fix" that breaks legitimate `pip -m` callers without closing the bypass is caught.
- **Determined operator overrides.** Role-deployed files at user-home paths can be overwritten by the user (`echo > ~/.npmrc`). The role isn't a sandbox. Tested implicitly via the precedence tests, but no test asserts "user can clobber if they want to."
- **The age-gate refresh timer.** The test image runs no systemd, so `49-age-gate-refresh.bats` drives `supply-chain-age-gate-refresh` directly and asserts the timer is absent. The service/timer units (the `User=` + `+ExecStart` split, `OnCalendar`, `Persistent=`) and the apply-time enable/disable tasks are only exercised on a real systemd host. Its `--sfw` step is driven against a stub sfw: a real sfw update (a new sfw-free release downloaded, verified and swapped in by root) is not exercised.
- **The shared-wrapper install paths for cargo's gate backend.** The test image's cargo is rustup's, in `/root/.cargo/bin`, so the role's own wrapper is never a system-path one there (`cargo_wrap_become` is always false). The root-owned copy in `/usr/local/libexec/supply-chain-hardening/cargo/` is exercised through the upgrade path in `40-upgrade-convergence.bats` (an older wrapper seeded at `/usr/local/bin/cargo`) and, for a fresh install, by `42-cargo-path-wrapper.bats`, which puts the toolchain's real cargo binary at `/usr/bin/cargo` and applies with the HOME of an account whose CARGO_HOME holds the pinned cargo-cooldown and no cargo: root's build then runs the copy and never that account's binary. A real apt cargo is not used (Ubuntu 24.04's 1.75 cannot build the backend, so it would only reach the degraded path). The pin-match condition on the copy and "a second deployer whose build fails keeps the first deployer's copy" are still covered only by manual repros on an apt-cargo container. The action's shared branch (`harden.sh` installing that copy with `$SUDO install -o 0 -g 0`) is not exercised at all: `tests/ci` always wraps a user-owned `TEST_BIN`, and run as root, its tests that stage a cargo-cooldown skip rather than write that host path.
- **Container CMD callers (no PAM).** `12-cross-ecosystem.bats` proves `/etc/environment` doesn't propagate; the config-file layer is the documented protection. Not separately re-tested for every ecosystem.

## Issues found by testing

1. **uv.toml config syntax error** — `require-hashes` was at the top level instead of under `[pip]`. uv silently rejected the entire config, disabling all uv hardening. Found during manual testing on n8n server.
2. **npm allow-git=none doesn't block before npm 11.9.0** — config is accepted but only enforced from npm 11.9.0 (MEASURED: 11.8.0 installs a git dependency with it set, and 11.2.0 to 11.8.x warn `Unknown ... config "allow-git"`). The role deploys the key except where the npm found warns about it; npm before 11.2.0 reads it but doesn't act on it. `tests/bats/03-npm.bats` has both a file-content check (always runs) and a behavioral check (skips below 11.9.0) — the behavioral check distinguishes "npm refused before network" (enforcement working) from "npm tried DNS for the bogus git URL" (key silently ignored).
3. **allow-git=none was not applied under setup-node's registry-url** — the key was in the npmrc files only, and `actions/setup-node` points `NPM_CONFIG_USERCONFIG` at its own `.npmrc`, so npm skipped `~/.npmrc` and installed a git dependency (MEASURED on npm 11.19.1 with harden.sh's files in place). Both surfaces now export `NPM_CONFIG_ALLOW_GIT=none` for npm 11.9.0+; `tests/ci/05-behavioral.bats` reproduces the redirect, with a FIXTURE CONTROL that is the bug.
4. **The role's verifier ran a checkout's pnpmfile** — its pnpm rows asked `pnpm config get` from the working directory, and in a project pnpm 10 and 11 load `.pnpmfile.cjs` / `.pnpmfile.mjs` and fetch `configDependencies` for that command too (MEASURED on 10.34.9, 11.0.0 and 11.28.13). They ask from `/` now, and the `pnpm repo config override` row reads `pnpm-workspace.yaml` itself (`tests/bats/52-env-layer-overrides.bats`, `tests/ci/07-verify.bats`).
5. **The verifier ran code other checkouts supply too, and so did the probes' /tmp** — run inside a checkout it ran its `.yarnrc.yml` `yarnPath` and plugins (yarn 1.22.22, 4.1.0 to 4.19.0), a `rust-toolchain.toml` `path =` toolchain through `cargo --version` (rustup 1.29.3), `.mvn/jvm.config` through `mvn -v` (maven 3.10.0), a `global.json` sdk-paths SDK through `dotnet --version` (.NET 10.0.404), `pip.py` through `python3 -m pip` and Poetry's `.poetry/plugins`; and its throwaway projects in `/tmp` picked up a `/tmp/.mvn/jvm.config`, `/tmp/Directory.Build.props` or `/tmp/rust-toolchain.toml` another account could plant (all MEASURED with marker files). Tools are asked from `/` now, the yarn settings are read as files (`yarn repo config override`), and the scratch dir comes from a base only root and the caller can write (`tests/ci/07-verify.bats`, `tests/bats/53-verifier-no-project-code.bats`).
6. **Eight per-user config files were replaced whole, with no copy and no message** — `~/.npmrc`, pnpm's two, `~/.yarnrc.yml`, `pip.conf`, `uv.toml`, the bunfig and `~/.bundle/config`, on both surfaces and on every run, login tokens and private registries included; the role also turned a 0600 `~/.npmrc` into 0644 (issue 48, MEASURED at d738db8). A token added after hardening went too, because the file carried the marker. Composer's `config.json` went the same way, and a credential added to cargo's, Maven's or NuGet's after hardening (MEASURED at 860a91c); so did npm's global config, and the role changed the mode of directories that were there, a 0750 home included. `~/.npmrc` is now merged and the others are replaced only when they are exactly what was last written. The tests found two more in the first version of the fix: with the block's end marker deleted the user's lines below it were taken for the block, and an in-place write over a bind mount could be cut short with no copy.
7. **pnpm's config was written where pnpm on macOS never looks** — `harden.sh` wrote `~/.config/pnpm` everywhere; pnpm on macOS reads `~/Library/Preferences/pnpm` unless `XDG_CONFIG_HOME` is set, so pnpm 11.29.0 and 12.23.0 ran a project's postinstall and took a release 9 hours old with everything hardened (MEASURED on hosted macos-15), while the verifier grepped the file it had written. Nothing in CI ran the Action on a Mac. `.github/workflows/macos.yml` does now, with the attacks.
8. **The role died half way on a Mac** — after `~/.npmrc` and `/etc/npmrc`, on a group name, while `--preflight` cleared the host. Its first task now refuses a macOS target (`50-preflight-gnu-date.bats`, and the real thing in `macos.yml`).
9. **"Already wrapped" was a grep for the project's name** — in `harden.sh` a tool script that mentions it was left unwrapped and reported as applied; in the role it was overwritten with no copy, and a wrapper `harden.sh` had written was moved over the real composer, bun or deno. Both read the marker line now.
10. **Two smoke jobs blamed the hardening for Maven Central's 429** — and the maven one's grep matched its own fixture's group id, so it could also read a refused run as a block. The verdict is a script tested on those runs' logs (`13-central-429.bats`).
11. **A version was read from an error message** — `harden.sh` merged stderr into `<tool> --version`, ignored the exit status and took the first number. With no network, corepack's yarn and pnpm (Node 22.23.5 under `~/.nvm`) print a stack trace with Node's version in its path, and both were reported "Fully applied" as 22.23.5 (MEASURED); found on a Mac where corepack could not start pnpm (#48). A command that fails now gives no version, stderr is not read, and npm, pnpm or yarn that is installed but gives none is degraded, not applied. So is pnpm before 10.16.0, which has no `minimumReleaseAge` and was also "Fully applied" (`tests/ci/02-validation.bats`).
12. **Root was taken to be able to write everywhere** — as root or with sudo, `harden.sh` moved a tool aside and wrote `/etc` with no check, so a tool in a read-only image or mount (bun, deno, cargo or composer), a tool mounted as a single file, or a read-only `/etc` ended the run under `set -e`: rc 1, no summary, every later ecosystem not applied (MEASURED on v2.1.0; reported from an AI agent's VM). Each is degraded now, and the run goes on (`tests/ci/09-intel-and-privilege.bats`). And a root without `CAP_CHOWN`, or with no such group in its user namespace, could not write a file of group `nogroup` and stopped on "could not write ~/.npmrc" (after item 6, before any release); it keeps the owner and gives no other group what it had. An owner that cannot be kept is still refused, with the reason. Looking for cases the other images had hidden found two tools it took for granted: `cmp`, which no Fedora, Arch, UBI, Rocky or Alma (minimal) image has (after item 6, before any release: a file with the user's settings stopped the run), and `xargs`, which Amazon Linux's does not (every run, v2.1.0 too). It needs neither now (`tests/ci/14-user-config.bats`).
13. **"Fully applied" for tools whose age gate does not exist** — `harden.sh` reported pip before 26.0, bun before 1.3.0 and composer before 2.11.0 as applied (bun and composer with a notice in the log), while the verifier called pip's gate a gap (reported from an AI agent's VM with pip 24.0). They are degraded now, with the reason, as npm, yarn and pnpm already were; a pip3 with no pip is judged too, and the role's `uv pip` is not (`tests/ci/02-validation.bats`).
